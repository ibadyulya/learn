# React

> 🌐 English version: [01-react.md](../en/01-react.md)

Библиотека для построения UI из компонентов. Читается как рассказ; опирается на
[функциональное программирование](../../02-paradigms-and-design/ru/02-functional-programming.md)
и [замыкания](../../01-js-typescript/ru/04-closures-scope.md).

Сквозная идея темы:

> **React — это `UI = f(state)`: ты описываешь, как выглядит интерфейс при данном
> состоянии, а не как его менять шаг за шагом. Меняешь состояние → React заново
> вычисляет разметку и **эффективно** обновляет реальный DOM через сравнение
> (reconciliation). Хуки дают состояние и эффекты функциональным компонентам.**

---

## Компонентная модель и декларативность

UI собирается из **компонентов** — функций, возвращающих разметку (JSX) по входным
данным. Ключевой сдвиг — **декларативность**: ты описываешь **результат** для текущего
состояния, а не императивно дёргаешь DOM (`el.textContent = ...`). «Как обновить» —
забота React.
```tsx
function Counter({ count }: { count: number }) {
  return <div>Count: {count}</div>;   // что показать при этом count
}
```
Данные текут **сверху вниз** (пропсы), в одну сторону — предсказуемо.

---

## Virtual DOM и reconciliation

Реальный DOM медленный в обновлении. React держит **лёгкую копию в памяти (virtual
DOM)**. При изменении состояния он строит новое виртуальное дерево, **сравнивает** со
старым (diffing) и применяет к реальному DOM **только различия** — это
**reconciliation**.
- сравнение идёт по позиции и **типу** элемента;
- в списках нужен **`key`** — стабильный идентификатор, чтобы React понял, какие
  элементы те же, а какие новые/удалённые (иначе перерисует лишнее или перепутает
  состояние). **Не индекс массива**, если список меняется.

---

## Хуки — состояние и эффекты в функциях

- **`useState`** — локальное состояние; изменение через сеттер **вызывает
  ре-рендер**.
  ```tsx
  const [count, setCount] = useState(0);
  setCount(c => c + 1);   // обновлять от предыдущего, не от замкнутого значения
  ```
- **`useEffect`** — побочные эффекты (запросы, подписки, таймеры) **после** рендера.
  Массив зависимостей управляет запуском; функция очистки снимает подписки/таймеры
  (см. [память/утечки](../../01-js-typescript/ru/09-memory-garbage-collection.md)).
  ```tsx
  useEffect(() => {
    const id = setInterval(tick, 1000);
    return () => clearInterval(id);      // cleanup
  }, []);                                 // [] = один раз при монтировании
  ```
- **`useMemo`/`useCallback`** — мемоизация дорогого значения/функции между рендерами.
- **`useContext`** — прокинуть данные без «prop drilling».
- **`useRef`** — изменяемая ссылка, не вызывающая ре-рендер (доступ к DOM, хранение
  значения между рендерами).

Правила хуков: звать **на верхнем уровне** компонента, всегда в одном порядке (React
сопоставляет их по порядку вызова).

---

## Модель ре-рендера и производительность

Изменилось состояние → компонент (и его поддерево) **перерисовывается** → reconciliation
→ точечное обновление DOM. Перерисовка **виртуальная и дешёвая**, но лишние — не
бесплатны. Оптимизация:
- **`React.memo`** — не перерисовывать компонент, если пропсы не изменились (по ссылке
  → отсюда важна [неизменяемость](../../02-paradigms-and-design/ru/02-functional-programming.md));
- **`useMemo`/`useCallback`** — стабилизировать пропсы-объекты/функции;
- корректные **`key`** в списках.
Не оптимизируй преждевременно — сначала измерь (React DevTools Profiler).

Тонкость с замыканиями: колбэк в хуке «замыкает» значения того рендера, где создан —
отсюда «stale closure» (устаревшее значение), лечится зависимостями и функциональным
обновлением сеттера.

## Где это всё рендерится (CSR, SSR, Next.js)

Всё выше — про React **на клиенте** (CSR): браузер получает почти пустой HTML и строит
UI из JS. Для senior важно знать и остальные стратегии — серверный рендеринг (SSR),
статическую генерацию (SSG/ISR), **гидратацию** и серверные компоненты (RSC), которые
даёт Next.js. Это отдельная большая тема — см.
[rendering-and-nextjs](./08-rendering-and-nextjs.md).

## Формулировка для собеса

> «React — декларативный UI как функция состояния: описываю, что показать при данном
> state, а не как менять DOM. Держит virtual DOM; при изменении состояния строит новое
> дерево, диффит со старым (reconciliation) и применяет к реальному DOM только различия;
> в списках нужен стабильный key. Хуки дают функциональным компонентам состояние
> (useState → ре-рендер), эффекты (useEffect с зависимостями и cleanup), мемоизацию
> (useMemo/useCallback), контекст, ref. Данные текут сверху вниз. Лишние ре-рендеры
> оптимизирую React.memo + стабильными пропсами (важна неизменяемость), но по замеру, не
> преждевременно. Помню про stale closure в хуках.»
