# Тестирование фронтенда

> 🌐 English version: [07-frontend-testing.md](../en/07-frontend-testing.md)

Как тестировать UI, чтобы тесты помогали, а не мешали. Читается как рассказ; общие
принципы тестов см. в
[backend-testing](../../04-backend/ru/08-backend-testing.md), здесь — специфика UI.

Сквозная идея темы:

> **Тестируй UI так, как им пользуется человек: проверяй **поведение** (что видит и
> делает пользователь), а не детали реализации (внутренний state, имена методов).
> Пирамида та же: много быстрых unit, меньше интеграционных, совсем мало e2e в реальном
> браузере.**

---

## Пирамида на фронте

Как и на бэке (см. [backend-testing](../../04-backend/ru/08-backend-testing.md)):
- **Unit** — чистые функции, хуки, отдельные компоненты в изоляции; быстро, их
  большинство.
- **Integration** — несколько компонентов вместе + замоканный API: проверяем, что фича
  работает как целое (форма отправляет данные, список рисует ответ).
- **E2E** — весь сценарий в **настоящем браузере** через реальный UI (Playwright,
  Cypress): регистрация → логин → заказ. Максимум уверенности, но медленно и хрупко — их
  мало.

Большинство ценности на фронте — в **интеграционных** тестах компонентов: они близки к
реальному использованию и не так хрупки, как e2e.

---

## Инструменты

- **Runner**: **Jest** или **Vitest** (запуск, ассерты, моки).
- **Компоненты**: **React Testing Library** / **Vue Test Utils** — рендер компонента и
  взаимодействие с ним.
- **E2E**: **Playwright** / **Cypress** — управляют реальным браузером.
- **Моки сети**: **MSW (Mock Service Worker)** — перехватывает HTTP на уровне сети, ближе
  к реальности, чем мок функции запроса.

---

## Философия Testing Library — «как пользователь»

Ключевая идея: **искать элементы так, как их видит пользователь**, а не по деталям
реализации.
```tsx
// хорошо: по роли/тексту, как воспринимает человек
screen.getByRole('button', { name: /отправить/i });
screen.getByLabelText('Email');
await userEvent.click(button);

// плохо: по классам/тест-id/внутреннему состоянию
container.querySelector('.btn-primary');   // хрупко к рефакторингу разметки
```
Зачем: тест, привязанный к структуре/классам/state, **ломается при рефакторинге**, хотя
поведение не изменилось. Тест «по пользователю» переживает рефакторинг и заодно проверяет
доступность (роли, лейблы).

---

## Что и как тестировать

- **Поведение и взаимодействия**: кликнул — увидел результат; ввёл невалидное — увидел
  ошибку. Не «стейт стал таким-то».
- **Не детали реализации**: имена внутренних функций, приватный state, структура DOM.
- **Мокать внешнее**: API (через MSW), время, случайность — чтобы тесты
  **детерминированы**.
- **Snapshot-тесты** — осторожно: большие снапшоты хрупки и их «обновляют не глядя»;
  полезны для мелких стабильных кусков.

Связь с общим правилом (см. [backend-testing](../../04-backend/ru/08-backend-testing.md)):
**тестируй поведение, а не реализацию** — на фронте это буквально «как пользователь».

---

## Формулировка для собеса

> «Фронт тестирую по пирамиде: много unit (функции, хуки, компоненты в изоляции), больше
> всего ценности в интеграционных тестах компонентов с замоканным API, и совсем мало e2e
> в реальном браузере (Playwright/Cypress). Инструменты: Jest/Vitest как раннер, React
> Testing Library / Vue Test Utils для компонентов, MSW для моков сети. Главный принцип
> Testing Library — искать элементы и взаимодействовать **как пользователь** (по
> роли/тексту/лейблу), а не по классам/тест-id/внутреннему стейту, чтобы тесты не ломались
> от рефакторинга и заодно проверяли доступность. Тестирую поведение, а не реализацию;
> внешнее (API, время) мокаю для детерминизма; snapshot — осторожно.»
