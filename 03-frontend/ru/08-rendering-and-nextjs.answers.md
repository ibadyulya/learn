# Рендеринг, SSR и Next.js — разборы

> 🌐 English version: [08-rendering-and-nextjs.answers.md](../en/08-rendering-and-nextjs.answers.md)

---

## Вопрос 1
Чистый SPA отдаёт **пустой HTML + большой бандл**; браузер должен скачать и выполнить JS,
прежде чем что-то покажет. Отсюда: **плохой SEO/превью** (краулер/бот соцсети видит пустую
страницу или обязан гонять JS), **долгий LCP/TTI** (белый экран, пока грузится/выполняется
JS) и **водопад запросов** (данные грузятся только после старта JS). Для первого показа и
SEO это плохо.

## Вопрос 2
- **CSR:** HTML в **браузере**, данные в рантайме; первый показ/SEO — плохо.
- **SSR:** HTML на **сервере на каждый запрос**, данные свежие; показ/SEO — хорошо, но
  TTFB и гидратация.
- **SSG:** HTML на **билде**, раздача с CDN; данные с момента сборки; показ/SEO — отлично,
  но не свежо.
- **ISR:** SSG + **фоновая перегенерация** по TTL/по требованию: статичная скорость +
  периодически свежие данные.

## Вопрос 3
1. Сервер сгенерил и прислал **готовый HTML** — пользователь его **видит**, но он «мёртвый»
   (нет обработчиков, состояния).
2. Браузер грузит **тот же** клиентский JS-бандл.
3. React **не строит DOM заново**, а проходит по **существующему** серверному DOM и
   **прицепляет** обработчики событий и внутреннее состояние компонентов.
4. После этого разметка становится **интерактивной**. Это и есть гидратация — «оживление»
   серверного HTML.

## Вопрос 4
**Hydration mismatch** — расхождение между HTML, сгенерированным **на сервере**, и первым
рендером **на клиенте**. Возникает от **недетерминированного** рендера: `Date.now()`,
`Math.random()`, `window`/`localStorage`, локаль/таймзона браузера, условный рендер по
клиентским данным. React ожидает совпадения; при расхождении ругается и может перерисовать/
сломать разметку. Избежать: держать **первый рендер детерминированным и одинаковым**, а
всё клиентозависимое откладывать в `useEffect` (выполнится уже после гидратации).

## Вопрос 5
SSR ускоряет **показ** (пользователь сразу видит серверный HTML), но чтобы страница стала
**интерактивной**, на клиент **всё равно** скачивается и выполняется весь JS-бандл для
гидратации — работа по JS не исчезает, только сдвигается. Борются: **RSC** (серверные
компоненты вообще не везут свой JS на клиент) и **partial/selective hydration** (гидрируем
только интерактивные острова, а не всю страницу) — так на клиент едет меньше JS.

## Вопрос 6
**RSC** рендерятся **только на сервере**: их код **не попадает** в клиентский бандл (0 JS),
и они могут напрямую обращаться к БД/файлам/секретам. **Клиентский компонент** (`'use
client'`) — интерактивный (useState/useEffect/onClick), едет на клиент и гидратируется.
Выгода: **меньше бандла** (статичное не тащим в браузер) и **нет клиентского водопада** за
данными — сервер уже сходил в БД при рендере. Разделяют: статика/данные → серверные,
интерактив → клиентские.

## Вопрос 7
Обычный SSR ждёт, пока **весь** HTML (включая медленные части с данными) сгенерится, и лишь
потом отдаёт — самый медленный запрос задерживает всю страницу. **Streaming + Suspense**
отдаёт HTML **частями по мере готовности**: быстрый каркас и контент — сразу, медленные
блоки (в `<Suspense>`) — потоком с фолбэком. Итог: раньше TTFB/LCP, страница не блокируется
самым медленным куском.

## Вопрос 8
- **(а) Блог с документацией** — контент публичный, редко меняется, важен SEO → **SSG**
  (раздача с CDN, молниеносно; ISR, если периодически правят).
- **(б) Лента персональных рекомендаций с SEO** — нужны и SEO, и **свежие/персональные**
  данные на запрос → **SSR** (или **RSC + streaming**: сервер собирает персональный HTML,
  стримит по мере готовности).
- **(в) Дашборд-редактор за логином** — SEO не нужен, много интерактива и приватные данные
  → **CSR**/клиентские компоненты (можно с небольшим серверным каркасом), не тратимся на
  SSR ради SEO, которого тут нет.
