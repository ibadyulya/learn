# Браузер, DOM и рендеринг

> 🌐 English version: [04-browser-dom-rendering.md](../en/04-browser-dom-rendering.md)

Как браузер превращает HTML/CSS в пиксели и почему это важно для производительности.
Читается как рассказ; событийную модель связывает с
[event loop](../../01-js-typescript/ru/01-event-loop.md).

Сквозная идея темы:

> **Браузер превращает HTML и CSS в картинку через конвейер: разобрать в деревья
> (DOM + CSSOM) → построить render tree → посчитать геометрию (layout) → закрасить
> (paint) → собрать слои (composite). Понимание этого пути объясняет, почему одни
> изменения дороги (reflow), а другие дёшевы, и как устроены события.**

---

## Критический путь рендеринга

От байтов к пикселям:
1. **HTML → DOM** — парсер строит **дерево DOM** из тегов.
2. **CSS → CSSOM** — из стилей строится **дерево CSSOM**.
3. **Render tree** — DOM + CSSOM объединяются в дерево видимых узлов со стилями
   (скрытое `display:none` не входит).
4. **Layout (reflow)** — считается **геометрия**: размеры и позиции каждого элемента.
5. **Paint** — узлы **закрашиваются** в пиксели (цвета, текст, тени) по слоям.
6. **Composite** — слои **собираются** на экране (в т.ч. на GPU).

JS может вмешаться на любом этапе (менять DOM/стили), что запускает пересчёт.

---

## Reflow против repaint — почему одни изменения дороже

- **Reflow (layout)** — пересчёт **геометрии**. Запускается изменением того, что влияет
  на размеры/позиции: ширина, шрифт, добавление/удаление узла, чтение `offsetHeight`.
  **Дорого** — может пересчитать большую часть дерева.
- **Repaint** — перерисовка **без изменения геометрии**: цвет, фон, видимость. Дешевле
  reflow.
- **Composite-only** — `transform`/`opacity` часто меняются **только на этапе
  composite** (на GPU), не трогая layout/paint — **самое дешёвое** (поэтому анимируют
  `transform`, а не `top/left`).

Оптимизация: **батчить** изменения DOM (не в цикле по одному), избегать «layout
thrashing» — чередования записи стилей и чтения геометрии (каждое чтение форсирует
reflow), анимировать `transform/opacity`.

---

## DOM — дерево, и оно дорогое

**DOM** — древовидное представление документа, API для чтения/изменения из JS. Операции
с DOM **дороже** обычного JS, потому что могут триггерить reflow/repaint. Поэтому
фреймворки (React/Vue) минимизируют реальные операции через virtual DOM/реактивность, а
руками — собирают изменения и применяют разом (`DocumentFragment`, батч).

---

## Событийная модель

Событие (клик) проходит **три фазы**: **capturing** (сверху вниз к цели) → **target**
(на элементе) → **bubbling** (вверх обратно к корню). По умолчанию слушатели срабатывают
на **всплытии**.

**Делегирование событий** — повесить **один** слушатель на общего родителя вместо
слушателя на каждый из тысяч детей: событие всплывёт, проверяешь `event.target`. Меньше
слушателей → меньше памяти, работает и для динамически добавленных элементов.

`event.preventDefault()` — отменить действие по умолчанию; `stopPropagation()` — прервать
всплытие.

---

## Связь с event loop

Рендеринг и JS делят **один поток** (см.
[event loop](../../01-js-typescript/ru/01-event-loop.md)): пока крутится тяжёлый JS,
браузер **не может отрисовать** кадр — страница «фризит». Поэтому тяжёлые вычисления
дробят/выносят в web workers, а обновления UI выравнивают под кадр через
`requestAnimationFrame`.

---

## Формулировка для собеса

> «Браузер строит из HTML дерево DOM, из CSS — CSSOM, объединяет в render tree, затем
> layout (геометрия) → paint (пиксели) → composite (слои). Изменения, влияющие на
> геометрию, вызывают дорогой reflow; цвет/фон — repaint подешевле; `transform/opacity`
> — только composite на GPU, поэтому анимирую их, а не `top/left`. DOM-операции дороги
> (триггерят пересчёт), поэтому батчу изменения и избегаю layout thrashing (чередования
> записи стилей и чтения геометрии). События идут capture → target → bubble; использую
> делегирование — один слушатель на родителе через всплытие. Рендер и JS в одном потоке,
> тяжёлый JS фризит кадр — дроблю/выношу в worker, анимации через requestAnimationFrame.»
