# Рендеринг, SSR и Next.js

> 🌐 English version: [08-rendering-and-nextjs.md](../en/08-rendering-and-nextjs.md)

Где и когда получается HTML и когда страница становится интерактивной. Читается как
рассказ; продолжает [React](./01-react.md), опирается на
[веб-производительность](./05-web-performance.md) и
[браузер/рендеринг](./04-browser-dom-rendering.md).

Сквозная идея темы:

> **Главный вопрос — ГДЕ рендерится HTML (в браузере или на сервере) и КОГДА страница
> становится интерактивной. CSR делает всё в браузере, SSR генерит HTML на сервере на
> каждый запрос, SSG/ISR — заранее. **Гидратация** «оживляет» серверный HTML на клиенте.
> Next.js даёт все стратегии плюс серверные компоненты (RSC) и стриминг.**

---

## Проблема чистого CSR (обычного SPA)

Классический SPA на React: сервер отдаёт почти **пустой** `<div id="root">` + большой
бандл JS. Дальше браузер: скачать JS → выполнить → построить DOM → (потом) сходить за
данными. Минусы для senior-масштаба:
- **плохой SEO и превью-шаринг** — краулер/бот соцсети видит пустую страницу (или обязан
  выполнять JS);
- **долгий LCP/TTI** — пользователь смотрит на белый экран, пока не скачался и не
  выполнился JS (см. [Core Web Vitals](./05-web-performance.md));
- **водопад запросов** — данные начинают грузиться только **после** старта JS.

Отсюда — вынести рендер (частично) на сервер.

---

## Стратегии рендеринга

- **CSR (Client-Side Rendering)** — рендер в браузере. Просто, полностью интерактивно
  после загрузки, но плохой первый показ и SEO. Годится за логином (дашборды), где SEO не
  нужен.
- **SSR (Server-Side Rendering)** — HTML генерится на сервере **на каждый запрос** и
  отдаётся готовым. Быстрый первый показ (контент виден сразу), хороший SEO, свежие/
  персональные данные — **ценой** нагрузки на сервер (TTFB) и необходимости **гидратации**.
- **SSG (Static Site Generation)** — HTML генерится **на этапе сборки**, раздаётся как
  статика с CDN. Молниеносно и дёшево, но данные «замерзают» на момент билда. Блоги, доки,
  лендинги.
- **ISR (Incremental Static Regeneration)** — SSG + **фоновая перегенерация** страниц по
  TTL или по требованию: статичная скорость + периодически свежие данные. Каталоги товаров.

| | CSR | SSR | SSG | ISR |
|---|---|---|---|---|
| Где рендер HTML | браузер | сервер (на запрос) | билд | билд + фон |
| Данные | в рантайме | на запрос (свежие) | на билде | периодически свежие |
| Первый показ / SEO | плохо | хорошо | отлично | отлично |
| Нагрузка на сервер | нет | на каждый запрос | нет (CDN) | низкая |

## Гидратация (hydration) — сердце темы

SSR отдал **готовый HTML** — пользователь его **видит**, но он «мёртвый»: обработчиков
событий нет, кнопки не кликаются, состояния нет. Затем на клиент грузится **тот же** JS,
React проходит по **уже существующему** серверному DOM и **прицепляет** к нему обработчики
и внутреннее состояние — «оживляет» разметку. Это и есть **гидратация**.

Три вещи, которые спрашивают:
- **«Uncanny valley» / потерянный интерактив** — окно, когда контент **виден, но не
  кликается** (JS ещё грузится/гидратируется). Клики в это время теряются → плохой **INP**.
- **Hydration mismatch** — если HTML **с сервера** и первый рендер **на клиенте**
  расходятся (использовал `Date.now()`, `window`, `Math.random()`, локаль браузера), React
  ругается и может перерисовать/сломать. Правило: **серверный и клиентский первый рендер
  должны совпадать**; недетерминированное откладывай в `useEffect`.
- **Стоимость** — SSR ускоряет **показ**, но весь JS **всё равно** скачивается и
  выполняется для гидратации. Отсюда идеи **partial/selective hydration** и RSC, чтобы
  везти на клиент меньше JS.

## React Server Components (RSC)

Компоненты, которые рендерятся **только на сервере**: их JS **не едет** на клиент
(нулевой вклад в бандл), и они могут напрямую ходить в БД/файлы/секреты. **Client
Components** (директива `'use client'`) — интерактивные, едут на клиент и гидратируются.

Идея разделения:
```
Server Component (по умолчанию в App Router): статичный контент, доступ к данным, 0 JS на клиент
  └─ Client Component ('use client'): интерактив (onClick, useState, useEffect)
```
Выгода: **меньше бандла** (статичное не тащим на клиент), нет клиентского водопада за
данными (сервер сходил в БД при рендере). RSC — это не замена SSR/гидратации, а другой
срез: **какие компоненты вообще нужны на клиенте**.

---

## Streaming SSR + Suspense

Вместо «сгенерить весь HTML → отдать одним куском» сервер отдаёт HTML **частями по мере
готовности**: быстрые части — сразу, медленные (ждут данные) — потоком, обёрнутые в
`<Suspense fallback={...}>`. Пользователь видит каркас и быстрый контент раньше, страница
не блокируется самым медленным запросом → лучше TTFB и LCP.

## Next.js — фреймворк поверх React

Даёт все стратегии «из коробки»:
- **App Router** (современный) — **RSC по умолчанию**, вложенные лейауты,
  `<Suspense>`/streaming, **Server Actions** (мутации прямо с сервера без ручного API);
  выбор стратегии на уровне запроса данных (кэшировать/ревалидировать).
- **Pages Router** (старый) — `getServerSideProps` (SSR на запрос), `getStaticProps`
  (SSG/ISR через `revalidate`), `getStaticPaths`.
- плюс: файловая маршрутизация, оптимизация картинок/шрифтов, автоматический code splitting
  по маршрутам, edge/node runtime.

Где что рендерится: **серверные компоненты** — на сервере (0 JS на клиент), **клиентские**
— рендерятся на сервере в HTML и затем **гидратируются** в браузере.

---

## Как выбирать стратегию

- публичный, редко меняющийся контент (блог, доки, лендинг) → **SSG** (+ **ISR**, если
  периодически обновляется);
- нужен SEO **и** свежие/персональные данные (лента, товар) → **SSR** или **RSC +
  streaming**;
- за логином, SEO не важен, много интерактива (дашборд, редактор) → **CSR** / клиентские
  компоненты;
- в реальности **смешивают** на уровне страниц и даже компонентов — Next это позволяет.

Правило: выбирай по **SEO, свежести данных и интерактивности**, а не «SSR всегда лучше».

## Формулировка для собеса

> «Ключевой вопрос — где рендерится HTML и когда страница интерактивна. CSR — всё в
> браузере (пустой HTML + JS): просто, но плохой LCP/SEO. SSR — HTML на сервере на каждый
> запрос: быстрый показ и SEO ценой TTFB и гидратации. SSG — HTML на билде, раздача с CDN:
> молниеносно, но данные статичны; ISR добавляет фоновую перегенерацию. Гидратация —
> клиент грузит тот же JS и «прицепляет» обработчики к серверному DOM; отсюда окно
> потерянного интерактива (INP), hydration mismatch при недетерминированном рендере и то,
> что бандл всё равно едет. RSC рендерятся только на сервере и не везут JS на клиент,
> client-компоненты (`'use client'`) — интерактив; streaming + Suspense отдаёт HTML
> кусками. Next.js даёт всё это: App Router с RSC по умолчанию и Server Actions, Pages
> Router с getServerSideProps/getStaticProps. Стратегию выбираю по SEO, свежести и
> интерактивности, часто смешивая.»
