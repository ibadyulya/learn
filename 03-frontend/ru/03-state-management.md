# Управление состоянием

> 🌐 English version: [03-state-management.md](../en/03-state-management.md)

Где и как хранить данные UI. Читается как рассказ; примыкает к
[React](./01-react.md) и [Vue](./02-vue.md).

Сквозная идея темы:

> **Состояние — данные, которые интерфейс показывает и меняет. Ключевой вопрос — не
> «какой стор взять», а **где** состоянию жить: локально в компоненте или глобально
> для многих. Глобальный стор нужен, когда данные разделяют далёкие части UI, — но не
> всё подряд туда; лишний глобальный стор усложняет.**

---

## Локальное vs глобальное состояние

- **Локальное** — живёт в компоненте (`useState`/`ref`): открыт ли дропдаун, текст в
  инпуте. Не касается других — держи рядом.
- **Глобальное** — общее для многих несвязанных компонентов: текущий пользователь,
  тема, корзина. Живёт в **сторе** или контексте.

Правило: **начинай с локального**, поднимай выше только когда данные реально нужны
нескольким. Преждевременный глобальный стор — оверинжиниринг.

---

## Проблема prop drilling

Если состояние высоко, а нужно глубоко, приходится **пробрасывать пропсы через много
слоёв** (`prop drilling`), которым эти данные не нужны — шум и связанность. Решения:
- **Context** (React) / provide-inject (Vue) — прокинуть данные вглубь без ручной
  передачи;
- **стор** — вынести общее состояние наружу компонентов.

---

## Flux — однонаправленный поток

Идея, на которой стоят Redux/Pinia: данные текут **в одну сторону**, изменения
предсказуемы.
```
действие (action) → обработчик меняет стор → представление читает стор → UI
        ▲                                                                  │
        └───────────────── пользователь взаимодействует ◄─────────────────┘
```
Никто не меняет стор «сбоку»: только через явные действия. Отсюда предсказуемость,
отладка «во времени» (time-travel), логируемость.

---

## Redux / Pinia

- **Redux** (React): единый **store**, изменения только через **actions** →
  **reducers** — **чистые функции** `(state, action) => newState`, возвращающие
  **новое** состояние (важна [неизменяемость](../../02-paradigms-and-design/ru/02-functional-programming.md);
  на ней стоит обнаружение изменений и time-travel). Современно — Redux Toolkit
  (меньше шаблона).
- **Pinia** (Vue): проще, использует реактивность Vue — стор с `state`/`getters`/`actions`,
  мутировать состояние можно напрямую (реактивность сама заметит).

Оба реализуют «единый источник истины» + однонаправленный поток; подписчики
обновляются при изменении (паттерн «наблюдатель»).

---

## Клиентское состояние ≠ серверное

Частая ошибка — тащить в Redux **всё**, включая данные с сервера. Но серверные данные —
это по сути **кэш** удалённого состояния со своими заботами (загрузка, кэш, ре-валидация,
устаревание). Для них лучше специальные инструменты — **React Query / SWR / TanStack
Query** (или Pinia Colada): они кэшируют ответы, отслеживают статус запроса и
инвалидируют. В глобальном сторе тогда остаётся только **клиентское** UI-состояние.

---

## Когда что

- **Локальное** — по умолчанию.
- **Context/provide** — тема, локаль, текущий юзер: редко меняется, нужно многим.
- **Стор (Redux/Pinia)** — сложное общее клиентское состояние, много взаимодействий.
- **Server-state библиотека** — данные с бэкенда (списки, сущности).

---

## Формулировка для собеса

> «Состояние делю на локальное (в компоненте) и глобальное (общее многим); по умолчанию
> держу локально и поднимаю только по реальной необходимости. Против prop drilling —
> context/provide или стор. Глобальные сторы (Redux/Pinia) реализуют flux:
> однонаправленный поток action → изменение стора → представление, единый источник
> истины; в Redux редьюсеры — чистые функции, возвращающие новое состояние (нужна
> неизменяемость, на ней стоят обнаружение изменений и time-travel). Серверные данные не
> держу в Redux — это кэш удалённого состояния, для него React Query/SWR со своим кэшем и
> ре-валидацией. Не выношу всё в глобал — это усложняет.»
