# Advanced TypeScript

> 🌐 English version: [03-advanced-typescript.md](../en/03-advanced-typescript.md)

Type-level программирование: generics, keyof/`T[K]`, mapped types, conditional
types, `never`, key remapping, `infer`, дистрибутивность, разбор утилитных
типов. Цель — не запомнить трюки, а уметь **вывести** тип вслух, как код.
Читается как рассказ; финальная якорная задача (`ExtractByType`) собирается из
кубиков, которые вводятся по очереди.

Сквозная идея всей темы: **типы в TypeScript — это второй язык
программирования, который работает при компиляции и оперирует типами так же, как
обычный JS оперирует значениями. Всё «продвинутое» — просто программирование на
этом языке.**

---

## Главный сдвиг в голове: типы — это второй язык

В TypeScript живут два языка одновременно.

Первый — обычный JavaScript. Работает в рантайме, оперирует **значениями**:
числами, строками, объектами.

Второй — язык типов. Работает **только при компиляции**, до запуска, и оперирует
**типами** так же, как первый оперирует значениями. И вот это ключевое: **типы
для второго языка — это его «значения».** Ты ими не просто помечаешь переменные —
ты их **вычисляешь**: берёшь один тип, преобразуешь, получаешь другой.

Когда ты пишешь `Partial<User>` — ты не «объявляешь тип». Ты **вызываешь
функцию** второго языка: на вход тип `User`, на выходе новый тип, где все поля
необязательные. `Partial` — функция, `User` — аргумент, результат — новый тип.

Как только это увидел, вся «продвинутая» TypeScript перестаёт быть набором
трюков и становится обычным программированием — просто на языке, где значения
это типы. У него есть:
- переменные и функции — **generics**;
- условия — **conditional types** (`extends ? :`);
- циклы по свойствам — **mapped types**;
- сопоставление с образцом и распаковка — **`infer`**;
- «пустое значение» — **`never`**.

Всё, что ниже, — это просто эти конструкции. Держи в голове: **мы пишем
программу, которая на входе получает типы и на выходе выдаёт типы.**

## Generics — это функции второго языка

Смотри на дженерик буквально как на функцию, только вместо круглых скобок —
угловые.

```ts
type Box<T> = { value: T };
```

Прочитай как определение функции: `Box` принимает параметр `T`, возвращает тип
`{ value: T }`. «Вызов»:

```ts
type StringBox = Box<string>;   // { value: string }
type NumberBox = Box<number>;   // { value: number }
```

Подставил `string` вместо `T` — ровно как аргумент в обычную функцию. Никакой
магии: `Box<T>` это `function Box(T) { return {value: T} }`, только на языке
типов.

У параметров бывают **ограничения** — через `extends`. Слово `extends` в TS
перегружено; в контексте параметра дженерика оно значит **«принимаю не любой
тип, а только такой, который подходит под вот эту форму»**:

```ts
type Lengthy<T extends { length: number }> = T;
// T extends {length: number}  ⟶  "T обязан иметь поле length: number"

Lengthy<string>;     // ок — у строки есть length
Lengthy<number[]>;   // ок — у массива есть length
Lengthy<number>;     // ошибка — у числа нет length
```

Читай `T extends U` как **«T годится в качестве U / является частным случаем
U»**. Это же слово встретится в условных типах и будет значить то же самое,
просто использоваться как вопрос. Запомни ощущение: **`extends` = "подходит ли /
является ли частным случаем"**.

## keyof и `T[K]` — читаем структуру типа

Два инструмента, чтобы работать с объектными типами: узнать ключи и достать тип
значения по ключу.

`keyof` берёт объектный тип и возвращает **юнион его ключей** (строковыми
литералами):

```ts
type User = { id: number; name: string; active: boolean };

type Keys = keyof User;   // "id" | "name" | "active"
```

Это не массив, а **юнион типов-литералов** — «или то, или то, или то».

`T[K]` — **индексный доступ**, «дай тип значения по ключу», как `obj[key]` в JS,
но на уровне типов:

```ts
type IdType = User["id"];       // number
type Vals = User[keyof User];   // number | string | boolean
```

Эти двое — `keyof T` (все ключи) и `T[K]` (тип значения по ключу) — наши рабочие
руки. Почти в каждой задаче ты берёшь ключи через `keyof`, а потом лазаешь по
значениям через `T[K]`.

---

## Mapped types — это цикл по свойствам

У нас есть `keyof T` — юнион ключей. Можно ли пройтись по ним и построить новый
объектный тип? Да. Это mapped type. Синтаксис пугает, но это буквально цикл по
ключам:

```ts
type Copy<T> = {
  [K in keyof T]: T[K]
};
```

Дословно: «для каждого `K` из `keyof T` — заведи ключ `K` со значением типа
`T[K]`». `[K in keyof T]` — шапка цикла, `K` — переменная, пробегающая юнион
ключей; `T[K]` справа — чтение значения по ключу. `Copy<T>` копирует тип один в
один, но теперь у нас есть **тело цикла**, где можно менять.

```ts
type Stringify<T> = { [K in keyof T]: string };

type User = { id: number; active: boolean };
type S = Stringify<User>;   // { id: string; active: string }
```

Так же под капотом работают встроенные утилиты — их можно написать самому:

```ts
type MyPartial<T>  = { [K in keyof T]?: T[K] };          // все поля необязательны
type MyReadonly<T> = { readonly [K in keyof T]: T[K] };  // все readonly
```

Держим в голове: **mapped type = цикл по ключам, строит новый объект.**

## Conditional types — это `if` второго языка

Выглядит как тернарник, работает как `if` на уровне типов:

```ts
type IsString<T> = T extends string ? true : false;

type A = IsString<"hello">;   // true
type B = IsString<42>;        // false
```

То самое `extends`, и значит то же — **«T подходит под / является частным
случаем»**, только теперь как **вопрос**: `T extends string ?` = «T — это
строка? да → первая ветка, нет → вторая».

```ts
type ElementType<T> = T extends any[] ? "массив" : "не массив";
ElementType<number[]>;   // "массив"
ElementType<string>;     // "не массив"
```

Теперь у нас есть цикл (mapped) и условие (conditional). Осталась одна деталь —
`never`.

---

## `never` — «этого ключа нет»

`never` — самый недопонятый тип. Формально это «тип, у которого нет ни одного
возможного значения» (функция, которая никогда не возвращает, а всегда кидает,
имеет возврат `never`). Но для наших задач важно **одно практическое свойство**,
и оно волшебное:

**Если в mapped type назначить ключу `never` в позиции ключа — этот ключ исчезнет
из результата.** Не станет ключом со значением `never` — **пропадёт целиком.**
Как будто ты сказал «а этого поля тут не будет».

Это свойство — «`never` в позиции ключа = удалить ключ» — и есть механизм, чтобы
**отфильтровывать** ненужные поля. Запомни отдельно, это ядро задачи. Но чтобы
поставить `never` именно в *позицию ключа*, нужна последняя деталь.

---

## Key remapping — переименование ключа через `as`

По умолчанию mapped type сохраняет ключ. Но его можно **переназначить** — через
`as` прямо в шапке цикла:

```ts
type T = {
  [K in keyof Obj as НовыйКлюч]: Obj[K]
};
```

`as` говорит: «ключ в результате будет не `K`, а вот этот». Обычно так
переименовывают поля. Но фокус: **если вычислить `as ... never` — ключ
исчезнет** (стыковка с предыдущим пунктом). А если в позиции `as` поставить
условие:

```ts
[K in keyof T as (условие) ? K : never]
```

«для каждого ключа `K` — если условие выполнено, оставь ключ как `K`; если нет —
переименуй в `never`, то есть **выкинь**». Это фильтр по ключам: условие — сито,
`never` — мусорка.

## Собираем `ExtractByType<T, U>` (якорная задача с собеса)

Дан объектный тип `T`, надо оставить только те поля, у которых **тип значения
подходит под `U`**.

```ts
type SomeType = { f1: number; f2: boolean; f3: string; f4: boolean };
// ExtractByType<SomeType, boolean>  ⟶  { f2: boolean; f4: boolean }
```

Собираем по шагам:

**Шаг 1 — цикл по ключам** (mapped type), пока просто копия:
```ts
type ExtractByType<T, U> = { [K in keyof T]: T[K] };
```

**Шаг 2 — хотим фильтровать ключи**, значит условие в позиции ключа через `as`:
```ts
type ExtractByType<T, U> = { [K in keyof T as ...условие...]: T[K] };
```

**Шаг 3 — условие**: «тип значения `T[K]` подходит под `U`?» это `T[K] extends U`.
Да → оставляем ключ `K`, нет → `never` (выкидываем):
```ts
type ExtractByType<T, U> = {
  [K in keyof T as T[K] extends U ? K : never]: T[K]
};
```

Проверка на `ExtractByType<SomeType, boolean>`:
- `f1`: `number extends boolean`? нет → `never` → **выкинут**;
- `f2`: `boolean extends boolean`? да → **оставлен**;
- `f3`: `string extends boolean`? нет → **выкинут**;
- `f4`: `boolean extends boolean`? да → **оставлен**.

Результат: `{ f2: boolean; f4: boolean }`. Ровно то, что просили.

Красота в том, что вся задача — это **три общих инструмента**: цикл
(`[K in keyof T]`), условие (`T[K] extends U ?`) и `never`-как-«выкинуть» через
`as`. Ни один не про «эту конкретную задачу». Дадут вариант — меняешь только
условие, каркас тот же. Например, обратная задача (выкинуть совпадающие) — просто
поменять ветки местами:

```ts
type ExcludeByType<T, U> = {
  [K in keyof T as T[K] extends U ? never : K]: T[K]
};
```

## `infer` — «поймай мне вот этот кусок типа»

Пока мы умели читать структуру, которая уже есть (`keyof`, `T[K]`). Но часто
нужно **вытащить тип, спрятанный внутри другого типа**: «дан тип функции — достань
тип того, что она возвращает». Заранее ты не знаешь, что там, — тип надо
*поймать*. Для этого `infer`.

Работает **только внутри условного типа** и означает буквально: «я не знаю, что
здесь стоит, — назови это переменной и дай мне её».

```ts
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

type A = MyReturnType<() => string>;         // string
type B = MyReturnType<(x: number) => User>;  // User
type C = MyReturnType<number>;               // never — не функция, образец не совпал
```

Читай как сопоставление с образцом: «`T` подходит под форму *функция, которая
возвращает нечто*? Это *нечто* назови `R`. Подошло → верни `R`, нет → `never`».

Интуиция: **`infer R` — это дырка в образце, куда TypeScript сам подставит то,
что там реально стоит, и вернёт под именем `R`.** Ты описываешь форму с дыркой,
движок сопоставляет и заполняет. Дырку можно ставить где угодно в образце:

```ts
type ElementOf<T> = T extends (infer E)[] ? E : never;
ElementOf<string[]>;   // string  — «массив из чего-то? назови это E»

type FirstArg<T> = T extends (first: infer F, ...rest: any[]) => any ? F : never;
FirstArg<(x: number, y: string) => void>;   // number
```

Нюанс: `infer` живёт **только в позиции после `extends`** в условном типе. В
обычном mapped type или просто так его не написать.

## Дистрибутивность — условный тип «размазывается» по юниону

Тонкое место, любят на собесе. Логика подсказывает один ответ, TypeScript даёт
другой:

```ts
type ToArray<T> = T extends any ? T[] : never;
type X = ToArray<string | number>;   // string[] | number[]  — НЕ (string|number)[]
```

Что произошло: TS не взял юнион целиком, а **разложил на члены, применил условный
тип к каждому по отдельности и собрал обратно в юнион**:

```
ToArray<string | number>
=  ToArray<string> | ToArray<number>     ← разложил
=  string[]        | number[]            ← применил к каждому
```

Это и есть дистрибутивность — как умножение по сложению: `2*(3+4) = 2*3 + 2*4`.

**Условие включения:** дистрибутивность срабатывает, только если проверяемый тип
— «голый» параметр (сам `T` слева от `extends`, не завёрнутый). Рубильник для
отключения — обернуть обе стороны в кортеж:

```ts
type A<T> = T extends any ? T[] : never;       // голый T → ДИСТРИБУТИВНО
type B<T> = [T] extends [any] ? T[] : never;   // в кортеже → НЕ дистрибутивно

B<string | number>;   // (string | number)[]  — весь юнион разом
```

`[T] extends [U]` — стандартный способ сказать «не разбирай юнион, сравни как
есть» (например, проверить, что `T` — это *ровно* такой-то юнион).

**Почему на этом держится `Exclude`:**
```ts
type Exclude<T, U> = T extends U ? never : T;   // T голый → дистрибутивно
Exclude<"a" | "b" | "c", "a">
// "a" extends "a" ? never : "a"  → never
// "b" extends "a" ? never : "b"  → "b"
// "c" extends "a" ? never : "c"  → "c"
// never | "b" | "c"  →  "b" | "c"   (never в юнионе растворяется)
```
Без дистрибутивности `"a"|"b"|"c" extends "a"` целиком было бы ложью → вернулся
бы весь юнион, фильтр бы не сработал. Вся работа `Exclude`/`Extract`/
`NonNullable` держится на разложении по членам.

**Ловушка — `never` это пустой юнион.** Дистрибутивный тип раскладывает юнион на
члены; у `never` их ноль → условие применяется 0 раз → результат `never`
(«цикл прокрутился 0 раз»):
```ts
type R = Exclude<never, string>;   // never
```
Практический вывод: если в дистрибутивный тип случайно приедет `never`, он молча
вернёт `never`, ничего не сделав — источник тихих багов.

## Утилитные типы стандартной библиотеки

Почти все они — **не магия компилятора, а обычные типы поверх пройденных
механизмов**. Сгруппированы по механизму, чтобы видеть родство.

**Меняют модификаторы полей (mapped types):**
```ts
type Partial<T>  = { [K in keyof T]?: T[K] };            // все поля необязательны
type Required<T> = { [K in keyof T]-?: T[K] };           // все обязательны (снятие ?)
type Readonly<T> = { readonly [K in keyof T]: T[K] };    // все readonly
```

**Выбирают подмножество ключей:**
```ts
type Pick<T, K extends keyof T> = { [P in K]: T[P] };    // оставить только K
type Omit<T, K> = Pick<T, Exclude<keyof T, K>>;          // выкинуть K = Pick + Exclude
```
`Omit` стоит на плечах `Pick` и `Exclude`: «Pick по всем ключам, кроме этих».
На бэкенде каждый день: `Omit<User, "password">`.

**Фильтруют юнионы (conditional + never + дистрибутивность):**
```ts
type Exclude<T, U>    = T extends U ? never : T;              // убрать члены U
type Extract<T, U>    = T extends U ? T : never;             // оставить совпадающие
type NonNullable<T>   = T extends null | undefined ? never : T;
```

**Собирают объект:**
```ts
type Record<K extends keyof any, V> = { [P in K]: V };   // keyof any = string|number|symbol
```

**Вытаскивают типы из функций (infer):**
```ts
type ReturnType<T>  = T extends (...a: any[]) => infer R ? R : never;
type Parameters<T>  = T extends (...a: infer P) => any ? P : never;   // кортеж аргументов
// плюс Awaited<T> (распаковать промис, рекурсивно), InstanceType, ConstructorParameters
```

**Строковые (вот эти реально встроены в компилятор, сам не напишешь):**
```ts
Uppercase<"abc">  // "ABC"      Capitalize<"hello">   // "Hello"
Lowercase<"ABC">  // "abc"      Uncapitalize<"Hello"> // "hello"
```

Вывод: **вся стандартная библиотека типов — те же пять механизмов.** Модификаторы
→ mapped; выбор ключей → mapped + remapping; фильтр юнионов → conditional +
never + дистрибутивность; распаковка функций → infer. Не список для зубрёжки, а
знакомые приёмы.

---

## Формулировка для собеса

> «Система типов TypeScript — это отдельный язык, где значения это типы.
> Дженерики — его функции, `extends` в условном типе — его `if`, mapped type
> (`[K in keyof T]`) — его цикл по ключам, а `never` в позиции ключа удаляет
> ключ. Чтобы отфильтровать свойства объекта по типу значения, я иду по ключам
> mapped type-ом, а в key remapping через `as` ставлю условие
> `T[K] extends U ? K : never`: подходящие ключи остаются, остальные становятся
> `never` и выпадают. `infer` в условном типе распаковывает вложенный тип
> (например, возврат функции: `... => infer R ? R : never`). А условный тип по
> голому параметру ещё и дистрибутивен — раскладывается по членам юниона, на чём
> и построены `Exclude`/`Extract`. Поэтому почти все утилитные типы — не магия
> компилятора, а обычные типы поверх этих механизмов.»
