# Замыкания и область видимости

> 🌐 English version: [04-closures-scope.md](../en/04-closures-scope.md)

Одна из самых частых тем на собесе и источник половины «магии» JS. Читается как
рассказ: всё вырастает из одного правила про то, откуда функция берёт переменные.

Сквозная идея темы:

> **Функция берёт переменные из того места, где она была ОБЪЯВЛЕНА, а не где
> вызвана (лексическая область видимости). Замыкание — прямое следствие: функция
> «запоминает» это окружение и продолжает иметь к нему доступ даже после того, как
> внешняя функция завершилась.**

---

## Лексическая область видимости — «где объявлено, оттуда и берём»

Область видимости (scope) — где переменная доступна. В JS она **лексическая**:
определяется **местом в коде, где функция написана**, а не откуда её позвали.

```ts
const x = 'внешний';
function outer() {
  const x = 'внутренний';
  function inner() { console.log(x); }   // берёт x из места объявления
  return inner;
}
outer()();   // 'внутренний' — хотя вызвали снаружи
```
Движок, не найдя переменную в текущей функции, идёт **вверх по цепочке областей**
(scope chain) — к той функции, внутри которой эта объявлена, и так до глобальной.
Ключ: цепочка строится по **вложенности в коде**, а не по стеку вызовов.

## Что такое замыкание

**Замыкание — это функция вместе с «запомненным» окружением** (переменными из
области, где она создана). Функция уносит с собой ссылку на свои внешние переменные
— и они живут, пока жива функция, даже если породившая их функция уже отработала.

```ts
function makeCounter() {
  let count = 0;                 // локальная переменная
  return () => ++count;          // замыкает count
}
const next = makeCounter();
next(); // 1
next(); // 2   — count не исчез после выхода из makeCounter, живёт в замыкании
```
`makeCounter` завершилась, её кадр стека «снят» — но `count` не собран сборщиком
мусора, потому что на него **ссылается** возвращённая функция. Это и есть
замыкание: приватное, живучее состояние.

Два независимых счётчика не делят состояние — у каждого своё замыкание:
```ts
const a = makeCounter(), b = makeCounter();
a(); a(); // 2
b();      // 1 — своё count
```

## Классическая ловушка: `var` в цикле

Любимый вопрос. Почему тут печатается `3, 3, 3`, а не `0, 1, 2`?
```ts
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 3, 3, 3
```
`var` — **одна** переменная на всю функцию (function-scoped). Все три колбэка
замкнули **один и тот же** `i`; когда таймеры сработали, цикл давно закончился и
`i === 3`. Лечение — `let`, у которого **своя привязка на каждую итерацию**
(block-scoped):
```ts
for (let i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);
// 0, 1, 2 — каждый колбэк замкнул свою копию i
```
Это же различие `var`/`let` — суть темы: `let`/`const` живут в блоке `{}`, `var` —
во всей функции и всплывает (hoisting) в начало.

## Зачем замыкания нужны на практике

- **Приватность / модульный паттерн** — спрятать состояние, отдать только методы:
  ```ts
  const counter = (() => { let c = 0; return { inc: () => ++c, get: () => c }; })();
  ```
  Снаружи до `c` не добраться — только через методы. (До `#private`-полей это был
  главный способ инкапсуляции в JS.)
- **Фабрики функций / каррирование** — `const add = a => b => a + b` (замыкает `a`).
- **Колбэки и обработчики** — колбэк помнит переменные из места, где повешен.
- **Мемоизация** — кэш живёт в замыкании между вызовами.

---

## Обратная сторона: утечки памяти

Раз замыкание **удерживает** внешние переменные от сборки мусора, легко нечаянно
держать живым что-то большое: обработчик события, замкнувший тяжёлый объект и не
снятый, не даст этот объект собрать. Правило — снимай слушатели/таймеры, не
замыкай лишнего. (Подробнее — в [memory-garbage-collection](./09-memory-garbage-collection.md).)

## Формулировка для собеса

> «В JS лексическая область видимости: функция берёт переменные из места, где
> объявлена, а не откуда вызвана; не нашла — идёт вверх по scope chain. Замыкание —
> функция вместе с этим запомненным окружением: она сохраняет доступ к внешним
> переменным даже после завершения породившей функции, потому что держит на них
> ссылку. Отсюда приватное состояние (модульный паттерн, счётчики, каррирование).
> Классическая ловушка — `var` в цикле: одна function-scoped переменная на все
> итерации даёт 3,3,3; `let` создаёт привязку на итерацию и даёт 0,1,2. Замыкания
> же могут держать память живой — источник утечек.»
