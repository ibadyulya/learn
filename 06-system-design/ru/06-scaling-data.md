# Балансировка, репликация, шардинг

> 🌐 English version: [06-scaling-data.md](../en/06-scaling-data.md)

Блок B, продолжение [05-scaling](./05-scaling.md). Как масштабировать за пределы
stateless-слоя — трафик и, главное, **данные**.

Сквозная идея:

> **Приложение (stateless) масштабировать легко — инстансы за балансировщик.
> Настоящая боль — база данных: она stateful, её так просто не размножишь.
> Репликация и шардинг — два разных ответа на «как масштабировать БД». Ключ:
> репликация = одни и те же данные во многих копиях; шардинг = разные данные на
> разных узлах.**

---

## Где узкое место

Слой приложения масштабируется **легко**: инстансы stateless (см. 05), добавил
копий за балансировщик — готово, они взаимозаменяемы. Но состояние мы вынесли
**в БД** — а она **stateful**: хранит данные, которые нельзя потерять и надо
держать согласованными. Её не размножишь как stateless-инстансы — сразу встаёт
«как копии держать в синхроне». **Поэтому масштабирование БД — отдельная сложная
тема, и в неё упирается вся система.**

## Балансировка нагрузки — раздать трафик

Углубление к [05](./05-scaling.md). На каком уровне работает (любят спросить):
- **L4 (транспортный)** — по IP/портам, не заглядывая в запрос. Быстро, тупо.
- **L7 (прикладной)** — понимает HTTP (URL, заголовки, куки), роутит умно
  (`/api/*` → одни, `/images/*` → другие). Гибко, но дороже.

Алгоритмы: **round-robin**, **least connections**, **weighted**, **IP hash**.
**Health-checks** — мёртвый инстанс автоматически выводится из ротации (это и
делает горизонталь самолечащейся).

Держи: **балансировщик = раздатчик перед stateless-слоем.** Приём трафика он
масштабирует, а саму БД за ним — нет. Для БД — инструменты ниже.

## Репликация — «одни данные, много копий»

Держать **полные копии одних и тех же данных** на нескольких узлах. Схема
**leader/follower** (master/replica, primary/secondary):

```
       записи (writes)
клиент ──────────────► LEADER
                         │ реплицирует изменения
              ┌──────────┼──────────┐
              ▼          ▼          ▼
          FOLLOWER   FOLLOWER   FOLLOWER   ◄── чтения (reads)
```
- **все записи → один leader**;
- leader **транслирует изменения** на followers;
- **чтения раздаём по репликам.**

Две выгоды (не путать):
1. **Масштаб чтений** — чтений обычно много больше записей; раскидал `SELECT` по
   репликам → размазал read-нагрузку. (Записи это НЕ масштабирует.)
2. **Отказоустойчивость (HA)** — упал leader → реплику **повышают** до нового
   leader (failover), данные не потеряны.

Проблема — **replication lag (задержка).** Изменение доезжает до реплик не
мгновенно. Тот же CAP/PACELC-трейд-офф:
- **синхронная** — leader ждёт реплики перед «записано»: надёжно/согласованно, но
  **медленно**;
- **асинхронная** — leader ответил сразу, реплики догонят: **быстро**, но чтение
  с реплики может вернуть **устаревшее** → **eventual consistency**.

Классический баг — **read-your-writes**: изменил профиль (в leader), тут же
перечитал (с отстающей реплики) → видишь старое. Лечат: чтение только что
записанного шлют на leader.

> **Репликация масштабирует ЧТЕНИЯ и даёт HA, ценой возможного отставания реплик
> (eventual consistency). Записи не масштабирует — все в один leader.**

## Шардинг — «разные данные на разных узлах»

Репликация упирается: все записи всё равно в один leader, и данные должны влезать
на одну машину. **Шардинг (партиционирование) — разрезать данные на куски и
разложить РАЗНЫЕ куски на РАЗНЫЕ узлы:**

```
Репликация:  узел1=[A,B,C]  узел2=[A,B,C]  узел3=[A,B,C]   ← одно и то же
Шардинг:     узел1=[A,B]    узел2=[C,D]    узел3=[E,F]     ← разные части
```
Каждый **шард** держит свой кусок и отвечает за записи/чтения только по нему.
Даёт:
1. **масштаб записей** — распределены по шардам, не давят в один leader;
2. **масштаб объёма** — данные больше не обязаны влезать в одну машину.

**Shard key — самое важное решение.** Поле, по которому режем (`user_id`):
- **range (диапазоны)** — 1–1000 → шард1 и т.д. Просто, хороши диапазонные
  запросы, но легко **перекос** (последний шард раскалится);
- **hash** — `hash(key) % N`. Равномерно, но диапазонные запросы бьют по всем
  шардам;
- **directory** — справочник «ключ → шард». Гибко, но сам узкое место.

Боль при плохом ключе:
- **hotspot** — нагрузка валит в один шард (шардили по стране, 80% из одной);
- **кросс-шард запросы / JOIN** — данные раскиданы → опрашивать все шарды и
  склеивать; JOIN между шардами почти невозможен. Поэтому связанное кладут на
  один шард (заказы юзера — туда же, где юзер);
- **ребалансировка** — добавить шард = перетасовать данные (смягчают consistent
  hashing).

> **Шардинг масштабирует ЗАПИСИ и ОБЪЁМ. Репликация про доступность, шардинг про
> ёмкость.**

## В реальности их комбинируют

Не «или-или», а вместе — решают разные проблемы:
- **шардинг** режет данные → масштаб записей и объёма;
- **репликация каждого шарда** → масштаб чтений по нему + HA.

```
Шард 1: leader + 2 реплики
Шард 2: leader + 2 реплики
Шард 3: leader + 2 реплики
```
Каждый шард — мини-кластер «leader + followers». Так устроены MongoDB sharded
clusters, Cassandra, Vitess (MySQL).

## Вся картина

```
трафик → БАЛАНСИРОВЩИК → stateless-инстансы   (легко: копии)
                              ↓
                          БД (stateful — вот где сложно):
  РЕПЛИКАЦИЯ: копии одних данных   → масштаб ЧТЕНИЙ + HA (ценой lag/eventual)
  ШАРДИНГ:    разные данные по узлам → масштаб ЗАПИСЕЙ + объёма (ценой shard key)
  ВМЕСТЕ:     шардинг + репликация каждого шарда → и то, и другое
```

> Формулировка: «Слой приложения масштабируется легко — stateless за
> балансировщиком. Сложность в БД (stateful). Репликация — копии одних данных:
> записи в leader, чтения с реплик, масштабирует чтения и даёт failover, но
> реплики отстают (async → eventual consistency, тот же CAP-трейд-офф). Шардинг —
> разные данные по узлам по shard key: масштабирует записи и объём, но критичен
> ключ (иначе hotspot), кросс-шард запросы/JOIN дорогие. В реальности комбинируют:
> шардируют, и каждый шард реплицируют.»

**Ловушка на засыпку:** масштабирует ли репликация записи? **Нет** — все записи в
один leader. Записи масштабирует только **шардинг**. Путать эти два — самая частая
ошибка по теме.
