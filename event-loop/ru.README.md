# Event Loop (Node.js) — конспект

> 🌐 English version: [en.README.md](./en.README.md)

Материал для подготовки к senior fullstack JS собесу. Тема: как Node решает,
что выполнять следующим.

## 1. Четыре участника

Путаница почти всегда от того, что их мешают в кучу. Их четыре:

| Участник | Что это | Приоритет |
|---|---|---|
| **Call stack** | место, где крутится синхронный код прямо сейчас | пока не пуст — ничего другого не бежит |
| **Macrotask queue** | колбэки от `setTimeout`, `setInterval`, `setImmediate`, I/O | низкий |
| **Microtask queue** | `Promise.then/catch/finally`, продолжение после `await`, `queueMicrotask` | высокий |
| **`process.nextTick` queue** | только в Node, отдельная очередь | ещё выше промисов |

Механика планирования на примере `setTimeout(cb, 0)`: таймер отсчитывает время
**в фоне** (в браузере — Web API, в Node — libuv/C++), и когда готов —
**кладёт `cb` в очередь**. Сам колбэк просто ждёт своей очереди.

## 2. Алгоритм цикла (запомнить дословно)

Когда call stack опустел:

```
1. Слить ВСЮ microtask-очередь (в Node: сначала nextTick, потом промисы) — до дна.
2. Взять РОВНО ОДНУ макротаску, выполнить её до конца.
3. Снова слить ВСЮ microtask-очередь.
4. Взять следующую ОДНУ макротаску.
5. Повторять.
```

Два ключа:
- Микротаски дренятся **полностью** (включая те, что добавились по ходу дренажа).
- Макротаски берутся **по одной**, и между ними микротаски вычищаются заново.

Отсюда: бесконечная рекурсия в `nextTick`/промисах **замораживает** event loop —
до макротасок дело не доходит.

## 3. Карусель фаз libuv

В Node макротаски лежат не в одной очереди, а в нескольких — по фазам. libuv
гоняет их по фиксированному кругу, у каждой фазы своя очередь:

```
timers        → setTimeout / setInterval (у кого истекло время)
pending       → отложенные системные колбэки
idle/prepare  → внутреннее
poll          → I/O-колбэки (файлы, сеть); тут цикл "паркуется" и ждёт
check         → setImmediate
close         → 'close' события (socket.on('close'))
```

На собесе достаточно знать три: **timers**, **poll**, **check**.

## 4. Где живут микротаски и nextTick

**Их НЕТ на карусели фаз.** Фазы — уровень libuv (C). Очереди nextTick и промисов —
уровень Node/V8 (JS), сверху. Правило:

> После КАЖДОГО колбэка (и между фазами) Node сливает микро-очереди:
> сначала весь nextTick, потом все промисы.

То есть они не «место на карусели», а **турникет между каждым шагом**. Где бы ни
выполнился колбэк — сразу после него чистятся nextTick + промисы, и только потом
цикл идёт дальше.

Полный порядок приоритетов:
```
1) синхронный код на стеке   — пока стек не пуст, ничего другого
2) process.nextTick queue    — слить полностью
3) Promise microtask queue   — слить полностью
4) одна макротаска из текущей фазы libuv → и сразу назад к п.2
```

## 5. Гонка setTimeout(0) vs setImmediate

Ключевой факт: **`setTimeout(fn, 0)` в Node клампится до `setTimeout(fn, 1)`** —
минимум 1 миллисекунда.

**На верхнем уровне модуля порядок НЕДЕТЕРМИНИРОВАН:**
- если старт процесса был быстрым (< 1мс) → таймер не созрел → фаза timers
  пропускается → doходим до check → `setImmediate` первым;
- если старт был медленным (≥ 1мс) → таймер готов в фазе timers → `setTimeout`
  первым.

Зависит от скорости старта → «от железа». Это и есть «момент краски».

**Внутри I/O-колбэка порядок ГАРАНТИРОВАН — `setImmediate` раньше:**
колбэк I/O выполняется в фазе `poll`, а сразу за ней идёт `check` (setImmediate);
до `timers` цикл доберётся только на следующем витке.

```js
const fs = require('fs');
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
// ВСЕГДА: immediate, timeout
```

## 6. setImmediate vs process.nextTick — названия врут

- `process.nextTick` срабатывает **раньше** (микро-очередь, до движения цикла).
- `setImmediate` — **позже** (фаза check).

Мем-правило: «`nextTick` — не на следующем тике, а прямо сейчас; `setImmediate` —
не немедленно, а на фазе check».

## 7. Формулировка для собеса

> «На верхнем уровне порядок `setTimeout(0)` и `setImmediate` недетерминирован —
> из-за клампа таймера до 1мс это гонка, зависящая от скорости старта. Но внутри
> I/O-колбэка `setImmediate` гарантированно раньше, потому что фаза `check` идёт
> сразу за `poll`, а `timers` — только на следующей итерации.»

## 8. CommonJS vs ESM (кратко, детали — отдельный конспект)

Сам event loop одинаков. Практическое отличие для этой темы: в ESM есть
**top-level `await`**, который меняет момент старта таймеров относительно
микротасок; в CJS его нет. Асинхронная загрузка ESM также делает «медленный старт»
вероятнее — гонка чаще склоняется к таймеру. Гарантий по-прежнему нет.
