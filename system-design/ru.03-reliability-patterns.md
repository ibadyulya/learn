# Reliability-паттерны

> 🌐 English version: [en.03-reliability-patterns.md](./en.03-reliability-patterns.md)

Как сделать доставку надёжной: ack/nack, идемпотентность, transactional outbox,
retries + backoff, DLQ, rate limiting, crash recovery. Продолжение
[02-event-driven-messaging](./ru.02-event-driven-messaging.md); понятия
Kafka/Rabbit — в [04-kafka-vs-rabbitmq](./ru.04-kafka-vs-rabbitmq.md).

Сквозная идея всего блока:

> **В распределённой системе сеть ненадёжна, а процессы падают. Всё — ack,
> ретраи, идемпотентность, outbox, DLQ — это ответы на один жестокий факт:
> нельзя гарантировать, что сообщение доставлено и обработано ровно один раз.
> Ты не борешься с этим фактом, ты вокруг него инженеришь.**

## ack/nack — как брокер понимает, что сообщение обработано

Брокеру нужен способ узнать, дошло ли и обработалось ли сообщение. Это
**подтверждение (acknowledgement)**. Механика: брокер отдаёт сообщение, но **не
выбрасывает сразу** — держит «в подвешенном состоянии» (in-flight) и ждёт:

- **ack** — «обработал успешно» → только теперь брокер удаляет / сдвигает
  указатель;
- **nack** — «не смог» → брокер **вернёт в очередь** (перевыдаст) или отправит в
  DLQ.

Ключ: **сообщение живо, пока его явно не подтвердили** — страховка от потери.
Молчит потребитель (упал, завис) → брокер по таймауту / обрыву решает «не
обработано» и **выдаёт заново**.

### Где рождается «окно» для дублей (ответ на «двойные выполнения»)

```
1. получил сообщение
2. обработал (списал деньги)
3. отправил ack
```
Между 2 и 3 — **щель**. Упал ровно здесь (деньги списаны, ack не ушёл) → брокер:
«ack не пришёл → не обработано → выдам заново» → списание **второй раз**. Дубль.

Наоборот, ack **до** обработки (3 перед 2): подтвердил, начал, упал → брокер уже
выкинул сообщение → **обработка потеряна**. Это и есть две семантики:

- **ack после обработки** → at-least-once → риск **дубля**;
- **ack до обработки** → at-most-once → риск **потери**.

Щель между «сделал» и «подтвердил» неустранима. Потерю обычно не терпим →
выбираем **ack после обработки (at-least-once)** и **соглашаемся на дубли** →
обезвреживаем идемпотентностью.

## Идемпотентность — обезвредить повтор

**Идемпотентная операция — та, что при 1 и при 10 выполнениях оставляет систему
в одном состоянии.** Повтор ничего не добавляет.

- «выключатель в OFF» — идемпотентно; «переключи свет» (toggle) — нет.
- `balance = 100` — идемпотентно; `balance -= 10` — **нет** (5 повторов = −50).

Наш дубль из ack-щели — это «списать 10» дважды. Задача — сделать так, чтобы
**второе выполнение того же сообщения не имело эффекта**. Три приёма:

**1. Ключ идемпотентности (дедупликация).** У сообщения уникальный `id`
(или бизнес-ключ `payment_id`). Потребитель ведёт учёт обработанных:
```
видел id раньше?  да → ничего не делаю, просто ack (обезвреженный дубль)
                  нет → обрабатываю, сохраняю id как done, ack
```
Тонкость (любят на собесе): **сохранение id и сам эффект должны быть атомарны**
(одна транзакция БД). Иначе новая щель: обработал, но не записал id → упал →
повтор снова обработает. «Списать деньги» и «пометить id обработанным» коммитятся
вместе.

**2. Естественная идемпотентность через состояние.** Проектируй как «установить»,
а не «изменить»: `UPDATE order SET status='paid'` идемпотентно, `balance -= 10` —
нет.

**3. Уникальные ограничения БД.** `INSERT` с уникальным `order_id` → повтор упадёт
на constraint → ловим ошибку дубликата и ack-аем. База — сам дедупликатор.

### Круг замыкается
```
at-least-once (ack после обработки — не теряем)
  + идемпотентность (дедуп по id / состояние / constraint — не двоим эффект)
  = effectively-once (снаружи «ровно один раз»)
```
Полный ответ про «двойные выполнения»: дубли неизбежны из-за щели между
обработкой и ack → доставку делаем at-least-once, обработку идемпотентной →
вместе «ровно один раз», хотя честного exactly-once на доставке нет.

## Transactional Outbox — зеркальная щель на стороне продюсера

**Проблема двойной записи (dual write).** Продюсер должен сделать два дела:
1. записать заказ в **свою БД**;
2. опубликовать событие в **брокер**.

Это **две разные системы без общей транзакции** — атомарно не обернуть. Краш в
щели ломает всё:

- **БД → потом брокер**, упал между: заказ в базе есть, **событие не отправлено**
  → почта/склад не узнали. **Потерянное событие.**
- **брокер → потом БД**, упал между: событие улетело всем, **заказа в базе нет**
  → письмо про несуществующий заказ. **Фантомное событие.**

Порядком не лечится. Решение — **убрать вторую систему из опасного момента**:
писать только в БД, а туда мы умеем атомарно.

**Идея:** вместо «БД + брокер» делаем **одну транзакцию в одну БД**, пишем две
вещи — бизнес-данные и событие в таблицу `outbox`:
```sql
BEGIN;
  INSERT INTO orders (...);              -- бизнес-данные
  INSERT INTO outbox (event, payload);   -- событие «на отправку»
COMMIT;                                   -- атомарно: либо оба, либо ни одного
```
Промежуточного «заказ есть, события нет» больше не бывает — щель закрыта.

**Кто публикует — message relay** (publisher/forwarder), отдельный процесс:
```
читать из outbox неотправленные → опубликовать в брокер → пометить sent=true
```
Relay не обязан быть идеальным: опубликовал, но упал до пометки → на следующем
круге опубликует **ещё раз** → дубль в брокере → ловит **идемпотентный
потребитель**. То есть outbox даёт at-least-once на продюсере, дубли гасит
идемпотентность на потребителе.

**Два способа relay:**
- **Polling publisher** — периодический `SELECT ... WHERE sent=false`. Просто, но
  задержка и нагрузка на БД.
- **CDC (Change Data Capture)** — relay читает лог транзакций БД (WAL в Postgres)
  через **Debezium**, публикует мгновенно без опроса. Эффективнее, но сложнее.

### Две щели — один принцип

| Где щель | Между чем | Лечится |
|---|---|---|
| **Продюсер** | «записал в БД» ↔ «отправил в брокер» | **transactional outbox** |
| **Потребитель** | «обработал» ↔ «отправил ack» | **идемпотентность** |

Оба — «свести к одной атомарной операции + at-least-once + идемпотентность».

### Важно: ack тоже нельзя сделать атомарным

Частая ошибка — думать, что на консюмере можно закоммитить обработку **вместе с
ack** в брокер. Нельзя: ack — это сообщение в **брокер**, отдельную систему.
«commit в БД + ack в брокер» — **та же двойная запись**, что у продюсера.

Что *можно* атомарно — только то, что внутри одной БД:
```sql
BEGIN;
  UPDATE balance ...;                 -- бизнес-эффект
  INSERT INTO processed (message_id); -- пометка «id обработан»  (таблица = inbox)
COMMIT;                                -- ack сюда НЕ входит
```
Ack остаётся снаружи и ненадёжен — и это ок: упал до ack → перевыдача → дедуп по
id → просто ack. **Идемпотентность и существует, чтобы прикрыть неатомарный ack.**

Полная симметрия: с обеих сторон атомарно коммитим **только то, что в БД**
(бизнес-действие + метаданные о сообщении: outbox / inbox), а общение с брокером
выносим наружу и делаем at-least-once. Outbox и идемпотентность — **одно решение**
для исходящей и входящей щели.

**Kafka-оговорка (если копнут про exactly-once):** Kafka умеет настоящие
транзакции «прочитал → обработал → записал → сдвинул offset» атомарно — но
**только пока всё внутри Kafka** (Kafka-to-Kafka). Как только побочный эффект во
**внешней БД** (списать деньги в Postgres) — снова двойная запись, транзакция
Kafka не спасает. «Exactly-once в Kafka» — про потоковую обработку внутри Kafka,
не про «списал деньги ровно раз». Для внешних эффектов — всё равно at-least-once
+ идемпотентность.

> Формулировка: «Проблема двойной записи: БД и брокер — разные системы без общей
> транзакции, поэтому запись заказа и публикация события не атомарны, и краш
> между ними либо теряет событие, либо шлёт фантомное. Transactional outbox:
> событие пишется в таблицу outbox в той же транзакции, что и бизнес-данные, а
> отдельный relay (polling или CDC через Debezium) публикует его и помечает
> отправленным. Relay at-least-once, дубли гасит идемпотентный потребитель. То же
> самое зеркально на консюмере: ack тоже не атомарен, поэтому атомарно коммитим
> эффект + id обработанного сообщения, а перевыдачу гасим дедупом.»

## Retries + backoff — повторяем, но с умом

Не пришёл ack → брокер перевыдаёт = ретрай. Вопрос **как**. Наивное «упал →
повторяю сразу, по кругу» — ловушка:

- **retry storm** — бомбишь шквалом повторов и без того лежащий сервис, мешая ему
  встать;
- жжёшь CPU/сеть, крутя один провал тысячи раз;
- если сервис лёг от перегрузки — ретраи его **добивают**, он не встаёт никогда.

Значит повторять **не сразу и не бесконечно.**

**Backoff** — с каждой неудачей ждём дольше. Обычно **экспоненциальный** (пауза
удваивается): 1с → 2с → 4с → 8с → 16с. Не встал за секунду — дай передышку
подлиннее; экспонента быстро разводит попытки во времени.

**Jitter** — случайный разброс к паузе. Без него 10 000 упавших разом сообщений
ждут ровно 1с, 2с… и **повторяют синхронным залпом** (**thundering herd**). Jitter
(`4с ± случайное`) размазывает повторы равномерно. Правило: **backoff разводит
попытки во времени, jitter не даёт им синхронизироваться.**

**Ограничение попыток (max retries).** Провалы бывают двух сортов — ключевое
различение:
- **transient (временный):** сеть моргнула, перегрузка, дедлок — само пройдёт →
  **ретрай осмыслен**;
- **permanent (постоянный):** битый JSON, ссылка на несуществующего юзера, баг в
  обработчике — **ретрай бесполезен**, будет падать всегда. Это **poison
  message** («отравленное»).

Без предела отравленное сообщение застрянет навечно (выдал → упал → перевыдал →
…), **блокируя очередь**: один битый JSON останавливает весь конвейер. Куда его
девать → DLQ.

## DLQ — Dead Letter Queue

**Отдельная очередь, куда сообщение уходит, исчерпав все ретраи** («мёртвое
письмо» — почтовый термин: недоставленное, отложенное в сторону).
```
падает → ретрай (backoff) → ... → исчерпаны N попыток
   → перекладывается в DLQ и уходит из основной очереди
   → основная очередь разблокирована, остальные идут дальше
```
Зачем (назвать три):
1. **разблокировать конвейер** — отравленное убрано с дороги, здоровые идут;
2. **не потерять проблему** — лежит в DLQ, можно изучить причину;
3. **replay** — после фикса вернуть в основную очередь и обработать заново.

DLQ = **карантин**: не в основном потоке (не мешает), не в мусорке (не потеряно).
Вешаем **алерт** — попало в DLQ → «зайди разберись», часто симптом бага/упавшей
зависимости.

> Формулировка: «Ретраить с экспоненциальным backoff и jitter — иначе retry storm
> добьёт падающий сервис, а thundering herd будет бить залпами. Ретраи не
> бесконечны: transient сбой пройдёт сам, permanent (poison message) ретраить
> бессмысленно и он заблокирует очередь. После N попыток → DLQ (карантин):
> основной поток разблокирован, сообщение не потеряно, можно изучить и после
> фикса переиграть. На DLQ — алерт.»

## Rate limiting — ограничение скорости

Защитить систему, не давая обрабатывать/отправлять быстрее заданного темпа.
Зачем: не завалить внешний API с лимитами; не дать одному клиенту сожрать
ресурсы (защита от злоупотреблений/DDoS); держать свою БД в комфортных рамках.

**Token bucket («ведро с токенами»).** В ведро с постоянной скоростью капают
токены (10/сек), ёмкость ограничена (100). Запрос **забирает токен**: есть →
проходит, нет → тормозится. Фишка — **разрешает всплески (bursts)**: накопилось
полное ведро → залп из 100 запросов пройдёт разом. «Средняя скорость ограничена,
короткий всплеск допустим».

**Leaky bucket («дырявое ведро»).** Запросы наливаются сверху, **вытекают снизу
строго с постоянной скоростью**; перелив отбрасывается. Фишка — **сглаживает
выход в идеально ровный поток**, всплесков на выходе не бывает никогда.

Разница: **token bucket допускает всплески (тратишь накопленное), leaky bucket
выравнивает в постоянный поток.** API переживёт burst → token bucket; нужен
строго ровный темп → leaky bucket.

## Crash recovery — что при падении

Не отдельный паттерн, а проверка на прочность «что, если упадёт вот здесь». Если
понял ack/идемпотентность/outbox — ответ уже есть.

Принцип: **неподтверждённое сообщение (нет ack) не теряется** — брокер держит его
in-flight и **перевыдаёт** после падения. Обход по точкам краха:

| Упал… | Что с сообщением | Итог |
|---|---|---|
| до обработки | не тронуто, ack нет | перевыдача, с нуля — ок |
| в середине | БД-транзакция откатилась, ack нет | перевыдача, заново с чистого листа — ок |
| после commit, до ack | эффект + id закоммичены, ack нет | перевыдача → дедуп по id → ack — ок |

Средняя строка — почему выручает **транзакционность БД**: незакоммиченная
обработка сама откатывается, «полуобработанных» состояний не бывает (всё или
ничего). Атомарность БД + перевыдача + идемпотентность = работа не потеряется и
не задвоится.

> Формулировка: «Crash recovery держится на том, что неподтверждённое сообщение
> не теряется — брокер перевыдаёт после падения. Незавершённая обработка
> откатывается транзакцией БД, полуобработанных состояний не бывает. Повторную
> доставку гасит идемпотентность. В любой точке краха: либо начнём заново, либо
> распознаем дубль — но не потеряем и не выполним дважды.»
