# Масштабирование Node-приложений

> 🌐 English version: [en.05-scaling.md](./en.05-scaling.md)

Открывает блок B (scalability). Node-специфика: всё вытекает из того, что Node
однопоточный (см. модуль event-loop). Опирается на идею stateless, которая
дальше свяжется с балансировкой и репликацией.

Сквозная идея:

> **Node по своей природе однопоточный: один процесс = один event loop = одно
> ядро CPU, занятое твоим JS. Сколько бы ядер ни было в машине, один Node-процесс
> использует только одно. Из этого вытекает всё про масштабирование Node — и
> почему «дай машину помощнее» тут работает хуже, чем ожидаешь.**

---

## Ограничение: Node видит только одно ядро

У Node **один поток**, крутящий твой JavaScript. Это и сила (нет гонок потоков),
и ограничение: **твой JS исполняется на одном ядре.** Машина с 32 ядрами + один
процесс `node app.js` = загружено **одно** ядро, остальные простаивают.

> Оговорка: libuv держит фоновый пул потоков для части I/O, но **твой JS**
> (колбэки, обработка запросов, вычисления) — один поток. Для масштабирования
> важен именно он.

Отсюда два способа расти.

## Вертикальное масштабирование (scale up) — «машину помощнее»

Сделать **одну машину мощнее**: больше CPU/RAM, быстрее диск. Серверов не
добавляешь — раскармливаешь один.

Плюс: **проще некуда** — переехал на инстанс пожирнее, архитектура та же, ни
балансировки, ни синхронизации.

**Подвох для Node:** добавить ядер одному процессу **бесполезно** — он как
использовал одно, так и использует. Из вертикали Node-процессу помогает только
**более быстрое ядро** и **больше RAM**, но не количество ядер.

Общие минусы вертикали:
- **есть потолок** — самой мощной машины не существует;
- **единая точка отказа** — упала машина → лежит всё;
- цена топового железа растёт нелинейно.

## cluster — занять все ядра одной машины

Раз процесс = ядро, решение: **запустить несколько процессов Node, по одному на
ядро.** Это модуль **`cluster`**: главный процесс (master) порождает **воркеров**
(≈ по числу ядер), все слушают **один порт**, соединения раскидываются между
ними. Каждый воркер — **свой процесс, свой event loop, своё ядро**:

```
                   ┌── worker 1 (ядро 1)
клиенты → :3000 → master ── worker 2 (ядро 2)
                   └── worker 3 (ядро 3)
```

На практике вместо ручного `cluster` берут **PM2** (`pm2 start app.js -i max` —
воркер на каждое ядро + авто-рестарт упавших) или отдают это оркестратору.

**Важно: воркеры НЕ делят память** — отдельные процессы, у каждого своя куча.
Состояние в памяти одного воркера не видно другим → мостик к stateless.

## Горизонтальное масштабирование (scale out) — «больше машин»

Добавить **серверов** и раздать нагрузку. `cluster` — тот же приём внутри одной
машины; горизонталь — на нескольких машинах. Перед копиями — **балансировщик
(load balancer)**:

```
                    ┌── инстанс A (машина 1)
клиенты → load balancer ── инстанс B (машина 2)
                    └── инстанс C (машина 3)
```

Алгоритмы: **round-robin**, **least connections**, по хешу IP. Плюс
**health-checks** — не отвечает инстанс → трафик уводится с него.

Плюсы (чего не было у вертикали):
- **почти нет потолка** — нужно больше → добавил машин (облачный автоскейлинг);
- **отказоустойчивость** — упал инстанс → балансировщик увёл трафик, сервис жив;
- дешевле — много обычных машин выгоднее одной топовой.

Минус — **сложность** (балансировщик, управление флотом → Docker/Kubernetes,
сложнее деплой/отладка) и одно жёсткое требование ниже.

## Почему горизонталь требует stateless

Балансировщик шлёт запросы на **любой** инстанс. Если инстанс что-то **помнит в
своей памяти** — ломается:
```
запрос 1 → инстанс A → сессия легла в память A
запрос 2 → инстанс C → в памяти C сессии НЕТ → «вы не авторизованы»
```
Правило: **инстансы stateless** — любой обрабатывает любой запрос одинаково.
Состояние — **наружу, в общее хранилище**:
- сессии/кэш → **Redis**;
- данные → **БД**;
- файлы → **S3**, не локальный диск.

> **stateless-инстанс + состояние в общем хранилище = любой запрос на любой
> инстанс работает одинаково.** (Та же проблема уже у `cluster` — воркеры тоже
> не делят память.)

**Sticky sessions** — костыль: балансировщик всегда шлёт юзера на один инстанс,
позволяя держать состояние в памяти. Ломает отказоустойчивость (упал «его»
инстанс → потерял состояние) и равномерность. Правильно — **stateless + Redis**,
sticky временно.

## worker_threads — не путать с cluster (CPU-bound)

`cluster` и `worker_threads` решают **разные** задачи.

Node силён в **I/O-bound** нагрузке — операциях, которые в основном **ждут** (БД,
сеть, файлы). Один event loop жонглирует тысячами таких — ждать почти не стоит CPU.

Беда с **CPU-bound** работой — тяжёлым вычислением (видео, хеши, картинки,
гигантский JSON). Оно **не ждёт, а грузит процессор**, и однопоточный event loop
**блокируется**: пока считаешь, остальные запросы стоят. Один расчёт морозит весь
сервер.

**`worker_threads`** — настоящие потоки **внутри процесса**, которым отдают
тяжёлое вычисление, чтобы **не блокировать главный event loop**.

| | `cluster` | `worker_threads` |
|---|---|---|
| Что | несколько **процессов** | несколько **потоков** в одном процессе |
| Память | не делят | могут делить (SharedArrayBuffer) |
| Зачем | масштабировать **I/O-throughput** по ядрам | не блокировать loop на **CPU-bound** |
| Аналогия | много копий сервера | вынести тяжёлый расчёт в сторонку |

Коротко: **`cluster` — обслуживать больше запросов (занять ядра под I/O),
`worker_threads` — чтобы тяжёлое вычисление не морозило сервер.**

## Вся картина

```
одна машина, один процесс   →  1 event loop = 1 ядро (потолок Node)
        ↓ занять все ядра машины
cluster / PM2               →  несколько процессов на одной машине
        ↓ выйти за одну машину
horizontal scale-out        →  много машин за балансировщиком
                               ⚠ требует STATELESS (состояние → Redis/БД/S3)

особый случай CPU-bound     →  worker_threads (не блокировать loop)
```

> Формулировка: «Node однопоточный, один процесс упирается в одно ядро.
> Вертикальное масштабирование для Node ограничено — лишние ядра процесс не
> использует, помогает `cluster`/PM2 (процесс на каждое ядро). Дальше —
> горизонтальное: много инстансов за балансировщиком с health-checks, почти без
> потолка и отказоустойчиво, но требует stateless — состояние в Redis/БД/S3,
> иначе запрос на другой инстанс не найдёт данных. Для CPU-bound есть
> worker_threads, чтобы вычисление не блокировало event loop. Обычно комбинируют:
> cluster внутри машины + scale-out машин, часто через Kubernetes.»
