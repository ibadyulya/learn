# Уровни изоляции — разборы

> 🌐 English version: [01-isolation-levels.answers.en.md](./01-isolation-levels.answers.en.md)

---

## Вопрос 1
**Non-repeatable read.** T1 читает **одну и ту же строку** (id=7) дважды и
получает разные значения (100 → 150), потому что T2 между чтениями сделала
`UPDATE` и **закоммитила**. Данные настоящие (не черновик) — но картина внутри T1
несогласованна. Исчезает на **Repeatable Read** и выше.

## Вопрос 2
**Dirty read.** T2 прочитала `qty=0`, которое T1 ещё **не закоммитила**, а потом
T1 сделала `ROLLBACK` — значения 0 никогда не существовало. Минимальный уровень,
где исчезает — **Read Committed** (видно только закоммиченное).

## Вопрос 3
Разница — в **статусе чужих данных**:
- **dirty read** — читаешь **незакоммиченное** (черновик), который может
  откатиться → работаешь с тем, чего может не быть вообще;
- **non-repeatable read** — читаешь **закоммиченное** (данные реальны), но
  значение строки **поменялось между двумя твоими чтениями** → несогласованность
  внутри одной транзакции.

Коротко: dirty — «чужое незавершённое»; non-repeatable — «чужое завершённое, но
уже другое».

## Вопрос 4
- **non-repeatable** — меняется **значение существующей строки** (чужой `UPDATE`):
  перечитал ту же строку — другое значение;
- **phantom** — меняется **набор строк**, попадающих под условие (чужой `INSERT`
  или `DELETE`): перечитал тот же запрос с `WHERE` — другое количество строк.

Non-repeatable про `UPDATE` одной строки, phantom про появление/исчезновение
строк.

## Вопрос 5
- (а) «не читать незакоммиченное» → **Read Committed** (убирает dirty read);
- (б) «дважды прочитать строку и получить то же» → **Repeatable Read** (убирает
  non-repeatable read).

## Вопрос 6
**PostgreSQL по умолчанию — Read Committed. MySQL (InnoDB) по умолчанию —
Repeatable Read.** Про фантомы: по SQL-стандарту на Repeatable Read они возможны,
**но InnoDB на своём дефолтном RR их на практике предотвращает** (MVCC-снимок +
gap locks). То есть формально «да, стандарт допускает», фактически «MySQL на
дефолте фантомы в основном не даёт». Именно это различие «стандарт vs реализация»
и проверяют.

## Вопрос 7
Serializable должен гарантировать результат «как будто транзакции шли по очереди».
Это стоит параллелизма: СУБД либо агрессивно **блокирует** (транзакции ждут друг
друга), либо (PostgreSQL — **SSI**) отслеживает конфликты и при опасности
**откатывает** одну транзакцию с ошибкой сериализации (`serialization failure`).

Поэтому приложение на Serializable **обязано уметь ловить эту ошибку и
повторять** (ретраить) транзакцию — на Read Committed такого класса ошибок нет,
ретраи не нужны. (Связь с темой retries + backoff из system-design.)
