# Проектирование REST API — разборы

> 🌐 English version: [03-rest-api-design.answers.md](../en/03-rest-api-design.answers.md)

---

## Вопрос 1
`/getUser` кладёт **глагол в URL**, дублируя то, что уже выражает HTTP-метод. По REST
URL — существительное-ресурс, действие — метод: **`GET /users/5`**. Предсказуемо и
единообразно: тот же ресурс `/users/5` для чтения (GET), обновления (PATCH), удаления
(DELETE).

## Вопрос 2
- **`401 Unauthorized`** — «не аутентифицирован»: нет/просрочен токен, система не знает,
  кто ты. Сценарий: запрос без заголовка `Authorization`.
- **`403 Forbidden`** — «аутентифицирован, но нельзя»: кто ты — известно, прав не
  хватает. Сценарий: обычный юзер лезет в `/admin`.

## Вопрос 3
- **Safe** — не меняет состояние. **Idempotent** — повтор даёт тот же результат.

| Метод | Safe | Idempotent |
|---|:--:|:--:|
| GET | ✅ | ✅ |
| POST | ❌ | ❌ |
| PUT | ❌ | ✅ |
| PATCH | ❌ | ⚠️ обычно нет (зависит) |
| DELETE | ❌ | ✅ |

## Вопрос 4
`POST /orders` создаёт **новый** ресурс каждый раз → повтор (ретрай сети, двойной
клик) создаст два заказа/два списания. Решение на уровне API — **Idempotency-Key**:
клиент генерирует уникальный ключ и шлёт в заголовке; сервер запоминает результат по
ключу и на повтор с тем же ключом возвращает **тот же** ответ, не выполняя операцию
дважды. (То же, что идемпотентность в reliability-patterns.)

## Вопрос 5
Stateless = сервер **не хранит состояние сессии между запросами** в памяти; каждый
запрос самодостаточен (несёт токен и все параметры). Тогда **любой** инстанс за
балансировщиком может обработать **любой** запрос — можно добавлять инстансы
горизонтально без «липких» сессий. Состояние выносится в БД/кэш/токен.

## Вопрос 6
- (а) создан ресурс → **`201 Created`** (+ `Location`);
- (б) не прошло валидацию → **`422 Unprocessable Entity`** (или `400`);
- (в) удалили, тела нет → **`204 No Content`**;
- (г) дубликат email → **`409 Conflict`**.

## Вопрос 7
- **Offset** (`?page=2&limit=20` / `OFFSET/LIMIT`) — простой, но на **живых данных**
  сбоит: вставки/удаления сдвигают страницы (пропуски/дубли), и большие offset
  медленны (БД пролистывает всё до нужного).
- **Cursor** — «дай 20 записей после этого id/времени»: стабилен при изменениях и
  быстр (индексный поиск от курсора), но нельзя прыгнуть на произвольную страницу.
Cursor лучше для лент/бесконечной прокрутки и больших наборов.
