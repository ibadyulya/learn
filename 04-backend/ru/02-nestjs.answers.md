# NestJS — разборы

> 🌐 English version: [02-nestjs.answers.md](../en/02-nestjs.answers.md)

## Вопрос 1
Nest даёт: **модульность** (структура из `@Module`), **DI-контейнер** (внедрение
зависимостей вместо `new`), **TS-first + декораторы**, единые механизмы для
**валидации** (pipes), **авторизации** (guards), **сквозной логики** (interceptors) и
**обработки ошибок** (exception filters). Смысл — навязать архитектурный каркас, чтобы
большой проект не расползался; под капотом всё тот же Express/Fastify.

## Вопрос 2
**Провайдер** — класс с `@Injectable()`, который контейнер умеет создавать и
внедрять. Зависимости объявляются в **конструкторе**, а Nest сам подставляет
экземпляры (строит граф зависимостей). Связь с **DIP**: класс зависит от абстракции и
не создаёт зависимость сам (`new`), а получает снаружи — это и есть «инверсия
зависимостей» + dependency injection как приём.

## Вопрос 3
- **imports** — другие модули, чьи экспорты нужны;
- **controllers** — обработчики HTTP;
- **providers** — внедряемые сервисы этого модуля;
- **exports** — провайдеры, видимые снаружи.
Не экспортированный провайдер **приватен для модуля**: доступен внутри, но другие
модули его внедрить не смогут (инкапсуляция границы).

## Вопрос 4
По умолчанию — **singleton** (один экземпляр на всё приложение, создаётся при старте).
`REQUEST`-scope нужен, когда сервису требуется состояние **конкретного запроса**
(например, данные текущего пользователя/трейс). Он дороже: экземпляр создаётся **на
каждый запрос**, и «заражает» scope-ом всю цепочку зависимостей — больше аллокаций,
медленнее.

## Вопрос 5
```
Middleware → Guards → Interceptors(до) → Pipes → Хендлер → Interceptors(после) → Exception filters
```
- **Middleware** — раннее (логи, cors);
- **Guards** — пускать/нет (авторизация, `canActivate`);
- **Interceptors** — обёртка вокруг вызова (тайминги, трансформация ответа, кэш);
- **Pipes** — валидация и преобразование входа (DTO);
- **Хендлер** — метод контроллера;
- **Exception filters** — превращают исключения в HTTP-ответ об ошибке.

## Вопрос 6
- (а) роль admin → **Guard** (авторизация);
- (б) валидация тела → **Pipe** (`ValidationPipe` + DTO);
- (в) лог времени → **Interceptor** (оборачивает вызов, замеряет до/после);
- (г) исключение → JSON 400 → **Exception filter**.
Каждая забота — свой слой; смешивать (валидировать в guard, авторизовать в pipe) —
антипаттерн.

## Вопрос 7
Контроллер — это слой **координации** (роль Controller из GRASP), а не бизнес-логики.
В нём: разбор запроса (`@Param/@Body`), вызов сервиса, возврат результата. Не должно
быть: бизнес-правил, обращений к БД, сложных вычислений — всё это в провайдерах-
сервисах. Тонкий контроллер = высокая связность, легко тестировать и переиспользовать
логику вне HTTP.
