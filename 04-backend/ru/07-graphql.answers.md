# GraphQL — разборы

> 🌐 English version: [07-graphql.answers.md](../en/07-graphql.answers.md)

---

## Вопрос 1
- **Over-fetching** — эндпоинт отдаёт **больше** данных, чем нужно клиенту (получаешь
  весь объект ради одного поля) → лишний трафик.
- **Under-fetching** — одного эндпоинта **мало**, приходится делать много запросов,
  чтобы собрать экран (N+1 сетевых вызовов).
GraphQL решает оба: клиент одним запросом просит ровно нужные поля и связи.

## Вопрос 2
- **Схема** — типизированный контракт API: типы, поля, доступные query/mutation.
- **Резолвер** — функция, которая **добывает данные для конкретного поля** (из БД,
  сервиса). Движок, разбирая запрос, зовёт резолверы нужных полей и собирает ответ по
  запрошенной форме.

## Вопрос 3
**Query** (чтение), **Mutation** (изменение), **Subscription** (реалтайм-события,
обычно по WebSocket). Всё идёт через **один эндпоинт** (`POST /graphql`), в отличие от
множества URL в REST.

## Вопрос 4
**N+1:** запрос связанных данных (`users { orders }`) наивно делает 1 запрос за
списком + по запросу на заказы **каждого** пользователя. **DataLoader** собирает все
запрошенные id за один тик event loop и делает **один батч-запрос** (`WHERE id IN
(...)`), плюс кэширует результаты в пределах запроса — вместо N запросов один.

## Вопрос 5
1. **Кэширование** сложнее — нет URL-на-ресурс, HTTP-кэш/CDN плохо применимы.
2. **Сложность/глубина запроса** — клиент может запросить тяжёлое/рекурсивное → нужны
   лимиты глубины и стоимости (иначе DoS).
3. **Авторизация** на уровне полей, а не только маршрута — сложнее.
4. Выше **порог входа** (схема, резолверы, борьба с N+1).

## Вопрос 6
В REST ответ привязан к **URL ресурса** → HTTP-кэш и CDN кэшируют по URL «из коробки».
В GraphQL всё идёт **одним POST на один URL** с телом-запросом, ответы разные — по URL
не закэшируешь. Приходится кэшировать на уровне клиента (нормализованный кэш Apollo)
или по полям/persisted queries — сложнее.

## Вопрос 7
- **GraphQL** — когда **много разных клиентов** (мобилка, веб, партнёры) с разными
  нуждами и **богатыми связями**: каждый берёт свою форму одним запросом.
- **REST** — когда важны **простота, предсказуемая нагрузка и HTTP-кэш/CDN** (публичное
  API, статичные ресурсы), и клиентов немного с похожими запросами.
