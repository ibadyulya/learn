# Проектирование REST API

> 🌐 English version: [03-rest-api-design.md](../en/03-rest-api-design.md)

Как строить предсказуемые HTTP-API. Читается как рассказ; всё вырастает из идеи
«ресурсы + стандартные глаголы».

Сквозная идея темы:

> **REST — стиль проектирования API вокруг ресурсов: URL — это существительное
> (что), HTTP-метод — глагол (действие над ним), код статуса — результат. Сервер
> stateless: каждый запрос самодостаточен. Хорошее API предсказуемо — по URL и
> методу понятно, что произойдёт.**

---

## Ресурсы и глаголы

**URL называет ресурс (существительное), метод задаёт действие.** Не глаголы в
адресе:
```
GET    /orders          — список
GET    /orders/42       — один
POST   /orders          — создать
PUT    /orders/42       — заменить целиком
PATCH  /orders/42       — частично обновить
DELETE /orders/42       — удалить
```
Плохо: `/getOrders`, `/createOrder` — действие уже в методе. Вложенность для
связей: `GET /orders/42/items`.

---

## Коды статуса — результат

Класс кода говорит, что случилось:
- **2xx успех:** `200 OK`, `201 Created` (создан ресурс, + заголовок `Location`),
  `204 No Content` (успех без тела, напр. DELETE).
- **3xx** — редиректы.
- **4xx ошибка клиента:** `400` (плохой запрос), `401` (не аутентифицирован),
  `403` (аутентифицирован, но нельзя), `404` (нет ресурса), `409` (конфликт,
  напр. дубликат), `422` (валидация), `429` (rate limit).
- **5xx ошибка сервера:** `500`, `503` (недоступен).

Различай `401` (кто ты?) и `403` (тебе нельзя) — частый вопрос.

---

## Безопасность и идемпотентность методов

Два свойства (любят на собесе):
- **Safe (безопасный)** — не меняет состояние: `GET`, `HEAD`. Можно кэшировать и
  повторять свободно.
- **Idempotent (идемпотентный)** — повтор даёт тот же результат: `GET`, `PUT`,
  `DELETE`. `PUT /orders/42` дважды — состояние одно. **`POST` не идемпотентен** —
  два раза создаст два ресурса.

Отсюда практика: для небезопасных **POST** с риском дубля (оплата) вводят
**Idempotency-Key** — клиент шлёт уникальный ключ, сервер по нему дедуплицирует
(прямая связь с идемпотентностью из
[reliability-patterns](../../06-system-design/ru/03-reliability-patterns.md)).

---

## Statelessness — сервер не помнит клиента

REST-сервер **не хранит состояние сессии между запросами**: каждый запрос несёт всё
нужное (токен, параметры). Зачем: любой инстанс за балансировщиком обработает любой
запрос → горизонтальное масштабирование (см.
[scaling](../../06-system-design/ru/05-scaling.md)). Состояние — в БД/кэше/токене, не
в памяти процесса.

---

## Версионирование, пагинация, фильтры

- **Версия** — чтобы не ломать клиентов при изменениях: в пути (`/v1/orders`) или
  заголовке. Путь проще и нагляднее.
- **Пагинация** — не отдавать 100k записей разом: offset/limit (`?page=2&limit=20`)
  или cursor-based (стабильнее на живых данных).
- **Фильтры/сортировка** — через query: `GET /orders?status=paid&sort=-createdAt`.

---

## Единый формат ошибок

Ошибки — предсказуемой структурой, а не как попало:
```json
{ "error": { "code": "ORDER_NOT_FOUND", "message": "Order 42 not found", "details": [] } }
```
Клиент парсит одинаково для всех эндпоинтов. Код статуса — в HTTP, машинный `code` —
в теле.

---

## Формулировка для собеса

> «REST — проектирование API вокруг ресурсов: URL это существительное, HTTP-метод —
> действие, код статуса — результат (2xx успех, 4xx клиент, 5xx сервер; 401 «кто ты»
> vs 403 «нельзя»). GET безопасен и идемпотентен, PUT/DELETE идемпотентны, POST —
> нет, поэтому для критичных POST ввожу Idempotency-Key. Сервер stateless — состояние
> в токене/БД, что даёт горизонтальное масштабирование. Плюс версионирование, чтобы
> не ломать клиентов, пагинация (offset или cursor), фильтры через query и единый
> формат ошибок с машинным кодом.»
