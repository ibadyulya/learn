# Валидация и обработка ошибок

> 🌐 English version: [05-validation-error-handling.md](../en/05-validation-error-handling.md)

Как не пустить в систему кривые данные и как единообразно реагировать на ошибки.
Читается как рассказ.

Сквозная идея темы:

> **Правило номер один: не доверяй входу — валидируй на границе, до бизнес-логики.
> А ошибки обрабатывай централизованно и единообразно, отделяя ожидаемые (плохой
> ввод, нарушенное бизнес-правило → 4xx) от неожиданных (баги, падения → 5xx), и
> никогда не протекай внутренностями наружу.**

---

## Валидация на границе

Клиент может прислать что угодно (случайно или злонамеренно). Проверяй **на входе**,
единой точкой, а не разбрасывая `if` по коду:
```ts
// DTO + декларативные правила (class-validator в Nest)
class CreateUserDto {
  @IsEmail()               email!: string;
  @MinLength(8)            password!: string;
  @IsInt() @Min(18)        age!: number;
}
```
В Nest это делает **`ValidationPipe`** на слое pipes (см. [nestjs](./02-nestjs.md)):
не прошло — автоматически `400/422`, до контроллера дело не доходит. Вне Nest — Zod
/ Joi. Смысл один: **бизнес-логика получает уже проверенные данные** и не думает о
мусоре.

Валидируй и **тип, и границы, и инварианты** (email — формат, age ≥ 18), и не
доверяй «скрытым» полям (роль, цена не из тела клиента).

---

## Два сорта ошибок

Ключевое различение для стратегии:
- **Ожидаемые (operational)** — часть нормальной работы: не прошла валидация, нет
  ресурса, конфликт, нет прав. Их **предвидим** и превращаем в осмысленный **4xx** с
  понятным сообщением.
- **Неожиданные (programmer errors)** — баги, недоступная зависимость, необработанное
  исключение. Наружу — обезличенный **5xx** «что-то пошло не так», внутрь —
  подробный лог; чинить кодом.

Не путать: «email занят» — ожидаемая (409), «undefined is not a function» —
неожиданная (500).

---

## Централизованная обработка

Не оборачивай каждый хендлер в `try/catch` с ручным формированием ответа — заведи
**один** обработчик:
- в Nest — **exception filter** ловит выброшенные исключения и формирует HTTP-ответ;
  бизнес-код просто **бросает** типизированные ошибки (`NotFoundException`,
  `ConflictException`), фильтр переводит их в статус + единый формат;
- в Express — **error middleware** `(err, req, res, next)` в конце цепочки.

```ts
// бизнес-код: просто бросаем
if (!user) throw new NotFoundException('User not found');
// фильтр/middleware: единый JSON { error: { code, message } } + нужный статус
```
Выгода: **единый формат** ошибок (см. [REST](./03-rest-api-design.md)), нет дублей
обработки, логика чистая.

---

## Не протекай внутренностями

Наружу — только безопасное: код ошибки, человекочитаемое сообщение, при валидации —
список полей. **Нельзя** отдавать клиенту stack trace, SQL, пути, содержимое
исключений БД — это утечка и подсказка атакующему. Подробности → в лог (с
контекстом: request id, user id), наружу → обезличенный ответ.

---

## Fail fast и логирование

- **Fail fast** — падай на плохом состоянии рано (проверил вход/инварианты в начале),
  а не тащи мусор вглубь, где он проявится непонятной ошибкой.
- **Логируй с контекстом** — структурно (JSON), с корреляционным id, чтобы связать
  запись с запросом; уровни (error/warn/info). (Связь с
  [observability](../../06-system-design/ru/11-observability.md).)

---

## Формулировка для собеса

> «Вход не доверяю — валидирую на границе декларативно (DTO + class-validator/Zod), в
> Nest это ValidationPipe, до контроллера кривое не доходит. Ошибки делю на ожидаемые
> (валидация, not found, конфликт, права → осмысленный 4xx) и неожиданные (баги →
> обезличенный 5xx + подробный лог). Обрабатываю централизованно — exception filter в
> Nest или error-middleware в Express: бизнес-код бросает типизированные ошибки, один
> слой переводит их в единый формат ответа. Наружу не протекаю stack trace/SQL —
> детали только в лог с request id. Плюс fail fast и структурное логирование.»
