# NestJS

> 🌐 English version: [02-nestjs.md](../en/02-nestjs.md)

Фреймворк, приносящий в Node **структуру**. Читается как рассказ; ядро идеи —
внедрение зависимостей, прямое продолжение
[SOLID](../../02-paradigms-and-design/ru/03-solid.md) (DIP).

Сквозная идея темы:

> **Nest — это структура поверх Node/Express: приложение собирается из модулей, а
> зависимости не создаются внутри классов, а внедряются DI-контейнером. Всё
> строится на двух вещах — модули (организация) и провайдеры (внедряемые сервисы).
> Запрос проходит через конвейер перехватчиков (guards → interceptors → pipes →
> handler), и каждый слой отвечает за свою сквозную заботу.**

---

## Зачем Nest поверх Express

Голый Express даёт роутинг и middleware, но не диктует структуру — на большом проекте
это расползается. Nest приносит: **модульность**, **TS-first**, **DI-контейнер**,
**декораторы** и единые механизмы для валидации, авторизации, обработки ошибок. Под
капотом — тот же Express (или Fastify), но с архитектурным каркасом.

---

## Модули — единицы организации

`@Module` группирует связанное: контроллеры, провайдеры, импорты других модулей.
```ts
@Module({
  imports: [DatabaseModule],       // что берём у других
  controllers: [OrderController],  // обработчики HTTP
  providers: [OrderService],       // внедряемые сервисы
  exports: [OrderService],         // что отдаём наружу
})
export class OrderModule {}
```
Приложение — дерево модулей от корневого `AppModule`. Модуль = граница
(инкапсуляция + высокая связность из
[coupling/cohesion](../../02-paradigms-and-design/ru/06-coupling-cohesion-principles.md)):
провайдер виден снаружи, только если явно экспортирован.

---

## Провайдеры и DI — сердце Nest

**Провайдер** — класс (обычно `@Injectable()`), который можно **внедрить**. Вместо
`new` зависимости объявляются в конструкторе, а контейнер их подставляет:
```ts
@Injectable()
class OrderService {
  constructor(private repo: OrderRepository) {}   // внедрено контейнером
}
```
Это прямое **DIP**: `OrderService` зависит от абстракции, а не создаёт конкретику
сам. Контейнер (IoC) сам строит граф зависимостей и передаёт экземпляры. Выгода:
подменяемость (мок в тестах), единый жизненный цикл, слабая связанность.

По умолчанию провайдеры — **синглтоны** (один экземпляр на приложение); есть scope
`REQUEST` (новый на запрос) и `TRANSIENT` — но синглтон-скоуп самый частый и дешёвый.

## Контроллеры и маршрутизация

`@Controller` + декораторы методов принимают HTTP и **делегируют** сервисам (роль
Controller из [GRASP](../../02-paradigms-and-design/ru/04-grasp.md)):
```ts
@Controller('orders')
class OrderController {
  constructor(private orders: OrderService) {}
  @Get(':id') get(@Param('id') id: string) { return this.orders.find(id); }
  @Post()     create(@Body() dto: CreateOrderDto) { return this.orders.create(dto); }
}
```
Контроллер тонкий: разобрал запрос, позвал сервис, вернул результат; бизнес-логики в
нём нет.

## Жизненный цикл запроса — конвейер

Запрос проходит слои по порядку, каждый — своя сквозная забота:
```
Middleware → Guards → Interceptors(до) → Pipes → ХЕНДЛЕР → Interceptors(после) → Exception filters
```
- **Middleware** — самый ранний слой (как в Express): логирование, cors.
- **Guards** — «пускать или нет»: **авторизация**/аутентификация (`canActivate` →
  true/false).
- **Interceptors** — оборачивают вызов (паттерн «декоратор»): логирование времени,
  трансформация ответа, кэш — до и после хендлера.
- **Pipes** — **валидация и преобразование** входных данных (`ValidationPipe` +
  class-validator проверяет DTO; см.
  [validation](./05-validation-error-handling.md)).
- **Handler** — метод контроллера.
- **Exception filters** — ловят выброшенные исключения и формируют HTTP-ответ об
  ошибке.

Разделение по слоям = чистые роли: guard не валидирует, pipe не авторизует.

## Формулировка для собеса

> «Nest — структурный фреймворк поверх Express/Fastify: приложение из модулей,
> зависимости внедряются DI-контейнером (прямой DIP — классы зависят от абстракций,
> контейнер подставляет провайдеры; по умолчанию синглтоны). Модуль — граница с
> imports/providers/exports. Контроллер тонкий: принял запрос, делегировал сервису.
> Запрос идёт по конвейеру: middleware → guards (авторизация) → interceptors
> (сквозное вокруг вызова) → pipes (валидация/трансформация DTO) → хендлер →
> exception filters (ошибки в HTTP-ответ). Каждый слой — своя сквозная забота, что
> даёт высокую связность и тестируемость.»
