# Node.js

> 🌐 English version: [01-nodejs.md](../en/01-nodejs.md)

Что такое Node изнутри и какие примитивы он даёт для серверного JS. Читается как
рассказ; опирается на [event loop](../../01-js-typescript/ru/01-event-loop.md) и
[модули](../../01-js-typescript/ru/02-modules-cjs-esm.md).

Сквозная идея темы:

> **Node — это движок V8 (исполняет JS) + библиотека libuv (даёт асинхронный
> ввод-вывод и event loop) + C++-биндинги (доступ к файлам, сети, ОС). Твой JS
> крутится в одном потоке, но ждущие операции уходят в фон, поэтому Node силён на
> I/O-нагрузке и слаб на тяжёлых вычислениях.**

---

## Из чего состоит Node

- **V8** — движок JavaScript от Google: компилирует и исполняет JS.
- **libuv** — C-библиотека: даёт **event loop** и **асинхронный I/O** (файлы, сеть,
  таймеры), плюс фоновый **пул потоков** для операций, которые ОС не умеет делать
  неблокирующе.
- **Биндинги/ядро** — C++-мост и стандартные модули (`fs`, `http`, `net`, `crypto`),
  дающие JS доступ к системе, которого в браузере нет.

Итог: **JavaScript на сервере** с неблокирующей моделью.

---

## Однопоточность и I/O против CPU

Твой JS исполняется в **одном потоке** (см.
[event loop](../../01-js-typescript/ru/01-event-loop.md)). Ждущие операции (запрос в
БД, чтение файла) не блокируют поток — уходят в libuv, а колбэк вызывается по
готовности. Поэтому Node отлично держит **тысячи одновременных I/O-соединений**
(API-шлюзы, чаты, прокси).

Обратная сторона — **CPU-bound** работа (тяжёлый расчёт, обработка картинок)
**блокирует** единственный поток: пока считаешь, остальные запросы стоят. Решения —
вынести в `worker_threads`, отдельный сервис или очередь (см.
[масштабирование](../../06-system-design/ru/05-scaling.md)).

> Оговорка: часть I/O libuv делает через пул потоков (по умолчанию 4), но **твой JS**
> — один поток; именно он — узкое место при вычислениях.

## EventEmitter — событийная модель Node

Многое в Node построено на паттерне «наблюдатель»: объект испускает **события**, на
которые подписываются.
```ts
import { EventEmitter } from 'node:events';
const bus = new EventEmitter();
bus.on('order', (id) => console.log('заказ', id));   // подписка
bus.emit('order', 42);                                // событие
```
На `EventEmitter` стоят стримы, HTTP-сервер (`server.on('request', ...)`), процессы.
Важно: у эмиттера событие **`'error'`** особое — если на него нет слушателя,
непойманная ошибка **уронит процесс**.

## Стримы и буферы — данные по кусочкам

**Buffer** — участок сырых бинарных данных (то, чего нет в браузерном JS). **Stream**
— поток данных, обрабатываемый **порциями**, а не целиком в память.
```ts
// плохо для больших файлов: весь файл в память
const data = await readFile('huge.log');
// хорошо: поток, обрабатываем по кускам, память постоянна
createReadStream('huge.log').pipe(gzip).pipe(createWriteStream('huge.log.gz'));
```
Зачем: обрабатывать гигабайты при малой памяти, начинать работу до полной загрузки.
Ключевое понятие — **backpressure**: если приёмник медленнее источника, поток
притормаживает источник, чтобы не переполнить память. Стримы асинхронно итерируемы
(`for await...of`).

Четыре типа: Readable, Writable, Duplex, Transform.

## Обработка ошибок в Node

Разные механизмы под разные модели:
- **синхронно** — `try/catch`;
- **промисы/async-await** — `try/catch` вокруг `await` или `.catch`;
- **error-first колбэки** — старый стиль ядра: `(err, data) => { if (err) ... }`;
- **EventEmitter/стримы** — слушать событие `'error'`;
- крайняя сеть — `process.on('uncaughtException')` / `'unhandledRejection'`: годятся
  только для **логирования и корректного завершения**, не для «проглотить и жить
  дальше» (состояние процесса уже неизвестно).

## Формулировка для собеса

> «Node — это V8 плюс libuv плюс C++-биндинги: JS на сервере с неблокирующим I/O.
> Мой код — один поток event loop, но ждущие операции уходят в libuv и возвращаются
> колбэком, поэтому Node держит тысячи I/O-соединений; CPU-bound задачи блокируют
> поток — их выношу в worker_threads/очередь. Событийная модель — EventEmitter
> (на нём стримы и http). Большие данные обрабатываю стримами по кускам с
> backpressure, а не грузя в память целиком. Ошибки ловлю по модели: try/catch для
> sync/async, error-first для колбэков, событие 'error' для стримов; uncaughtException
> — только для логирования и graceful shutdown.»
