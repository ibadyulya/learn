# Валидация и обработка ошибок — разборы

> 🌐 English version: [05-validation-error-handling.answers.md](../en/05-validation-error-handling.answers.md)

---

## Вопрос 1
Валидация на границе гарантирует, что **в бизнес-логику попадают уже проверенные
данные** — она не засоряется проверками и не думает о мусоре (высокая связность). Это
единая точка, а не разбросанные `if`. В Nest — **`ValidationPipe`** на слое pipes:
проверяет DTO по декораторам (class-validator) до контроллера; не прошло → `400/422`
автоматически.

## Вопрос 2
- **Ожидаемые (operational)** — нормальная часть работы, предвидим → осмысленный 4xx:
  «email занят» (409), «нет прав» (403), «таймаут БД» (часто 503/повторяемая) —
  условно operational (внешняя зависимость).
- **Неожиданные (programmer)** — баги: «Cannot read property of undefined» → 500 +
  лог, чинить кодом.
Граница: предвидимое и осмысленное для клиента vs дефект кода.

## Вопрос 3
Централизованно = **один** обработчик формирует ответ по единому формату; хендлеры не
дублируют `try/catch`, бизнес-код просто **бросает** типизированные ошибки. В **Nest**
— **exception filter** ловит исключения и переводит в HTTP-ответ; в **Express** —
**error-middleware** `(err, req, res, next)` в конце цепочки. Итог: единый формат, нет
дублирования, чистая логика.

## Вопрос 4
Нельзя отдавать **stack trace, SQL-запросы, пути файлов, текст исключений БД,
внутренние коды** — это утечка информации и подсказка атакующему (структура, версии,
имена таблиц). Клиенту — только код ошибки + человекочитаемое сообщение (+ поля при
валидации). Детали → в **лог** с контекстом (request id, user id).

## Вопрос 5
**Fail fast** — обнаружить некорректное состояние и упасть **как можно раньше**
(проверка входа/инвариантов в начале), а не пропускать мусор вглубь. Иначе плохие
данные всплывут где-то далеко непонятной ошибкой, которую тяжело диагностировать.
Ранний явный отказ = проще отладка и меньше повреждений.

## Вопрос 6
`role` из тела клиента — это **данные под контролем атакующего**; доверять = дать
любому назначить себе admin (**privilege escalation**). Роль назначает **сервер** по
своей логике (по умолчанию `user`, повышение — отдельным авторизованным процессом).
Поля привилегий/цены/владельца никогда не берут из клиентского ввода — их
проставляет сервер.

## Вопрос 7
Статус **`400`** или **`422 Unprocessable Entity`**. Тело — единый формат со списком
проблемных полей:
```json
{ "error": { "code": "VALIDATION_FAILED",
  "message": "Validation failed",
  "details": [{ "field": "email", "message": "must be an email" },
              { "field": "age", "message": "must be >= 18" }] } }
```
Так клиент может показать ошибки у конкретных полей формы.
