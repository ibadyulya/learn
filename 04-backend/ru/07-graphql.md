# GraphQL

> 🌐 English version: [07-graphql.md](../en/07-graphql.md)

Альтернатива REST, где форму ответа задаёт клиент. Читается как рассказ; сравнение с
[REST](./03-rest-api-design.md) — сквозное.

Сквозная идея темы:

> **GraphQL — язык запросов к API: клиент одним запросом к одному эндпоинту сам
> указывает, какие поля и связи ему нужны, и получает ровно их. Это решает
> over/under-fetching REST, но переносит сложность на сервер (N+1, кэширование,
> ограничение сложности запросов).**

---

## Проблема REST, которую решает GraphQL

- **Over-fetching** — эндпоинт отдаёт больше, чем нужно (тянешь весь `user`, а надо имя).
- **Under-fetching / N+1 запросов** — чтобы собрать экран, дёргаешь много эндпоинтов
  (`/user`, потом `/user/1/orders`, потом по заказу...).

GraphQL: **один запрос** описывает нужную форму, сервер возвращает точно её:
```graphql
query {
  user(id: 1) {
    name
    orders { id total }     # связанные данные — в том же запросе
  }
}
```

---

## Схема, типы и резолверы

- **Schema** — строго типизированный контракт API: типы, поля, запросы, мутации.
  ```graphql
  type User { id: ID!, name: String!, orders: [Order!]! }
  type Query { user(id: ID!): User }
  ```
- **Resolver** — функция, которая **добывает** данные для конкретного поля (из БД,
  сервиса). Каждое поле может иметь свой резолвер; движок собирает ответ по форме
  запроса.

---

## Три типа операций

- **Query** — чтение (аналог GET).
- **Mutation** — изменение (создать/обновить/удалить).
- **Subscription** — подписка на события в реальном времени (обычно поверх
  WebSocket) — паттерн «наблюдатель».

Всё идёт через **один эндпоинт** (`POST /graphql`), в отличие от множества URL в REST.

---

## Проблема N+1 и DataLoader

Главная ловушка. Запрос `users { orders }` на 100 юзеров наивно сделает **1 запрос за
списком + 100 запросов за заказами** каждого — N+1.
Решение — **DataLoader**: собирает id за один тик и делает **один батч-запрос**
(`WHERE user_id IN (...)`), плюс кэширует в пределах запроса. Обязательный приём в
проде.

---

## REST vs GraphQL — трейд-оффы

| | REST | GraphQL |
|---|---|---|
| Форма ответа | сервер фиксирует | клиент выбирает |
| Эндпоинты | много (ресурсы) | один |
| Over/under-fetching | бывает | решено |
| HTTP-кэш | простой (по URL) | **сложнее** (один POST-URL) |
| Сложность запроса | ограничена | клиент может запросить тяжёлое → нужен лимит |
| Кривая входа | низкая | выше (схема, резолверы, N+1) |

GraphQL хорош при **многих клиентах с разными нуждами** (мобилка/веб), богатых
связях. REST проще, отлично кэшируется, предсказуемее по нагрузке.

---

## Подводные камни

- **Кэширование** — нет URL-на-ресурс, HTTP-кэш/CDN работают хуже; кэшируют на уровне
  клиента (Apollo) или поля.
- **Сложность/глубина запроса** — клиент может запросить рекурсивно-тяжёлое → нужны
  **лимиты глубины/стоимости**, иначе DoS.
- **Авторизация** — на уровне полей, а не только маршрута; сложнее.
- **N+1** — без DataLoader легко утопить БД.

---

## Формулировка для собеса

> «GraphQL — типизированный язык запросов: клиент одним запросом к одному эндпоинту
> указывает нужные поля и связи, решая over- и under-fetching REST. Сервер описывает
> схему (типы, query/mutation/subscription) и резолверы — функции добычи данных на
> поле. Главная ловушка — N+1 при связанных данных, лечится DataLoader (батчинг +
> кэш в запросе). Трейд-офф против REST: гибкость клиента ценой сложного кэширования
> (нет URL-на-ресурс), риска тяжёлых запросов (нужны лимиты глубины/стоимости) и
> пофайловой авторизации. Беру GraphQL при многих клиентах и богатых связях, REST —
> где важны простота и HTTP-кэш.»
