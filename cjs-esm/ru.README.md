# CommonJS vs ES Modules

> 🌐 English version: [en.README.md](./en.README.md)

Две системы модулей в JavaScript: что это, откуда взялись, чем отличаются и
почему это всплывает на собесе (в том числе в связке с event loop). Читается как
рассказ, а не как шпаргалка — идея в том, чтобы **понять**, а не запомнить.

Если коротко, вся тема сводится к одному различию, из которого дальше растёт
всё остальное: **CommonJS выясняет зависимости по ходу выполнения и синхронно,
а ES Modules — заранее и статически.** Держи эту фразу в голове, ниже всё будет
к ней возвращаться.

---

## Откуда вообще взялись модули

Представь ранний JavaScript. Он жил только в браузере, и весь код со страницы
сваливался в одно общее пространство имён. Подключил два `<script>` — и если в
обоих есть переменная `user`, они молча затрут друг друга. Никакой изоляции.
Пока скрипты были маленькие, это терпели.

Потом появился **Node.js** — JavaScript на сервере. А на сервере так жить уже
нельзя: серверное приложение — это сотни файлов, и если всё валится в общую
кучу, это ад. Нужен способ сказать: «вот этот файл — отдельная коробка. Внутри
свои переменные наружу не текут, а торчит только то, что я разрешил».

Вот это и есть **модуль**: файл как изолированная коробка с «окошком выдачи»
(что отдаём наружу) и «окошком приёма» (что берём у других).

Ключевой исторический факт, из которого растёт вся путаница: **Node-у модули
понадобились раньше, чем язык сам придумал стандарт.** Node не стал ждать и
сделал свой формат — **CommonJS (CJS)**. А через несколько лет уже в сам язык
завезли официальный стандарт — **ES Modules (ESM)**. Теперь эти двое живут бок
о бок. Отсюда весь дуализм, с которым мы возимся.

---

## CommonJS — «выполняй по ходу дела»

Node сделал модули самым простым возможным способом — **через обычные функции и
объекты**, без нового синтаксиса языка.

Отдать наружу — положить в специальный объект `module.exports`:

```js
// math.js
function add(a, b) { return a + b; }
module.exports = { add };
```

Взять чужое — вызвать функцию `require`, она вернёт тот самый объект:

```js
// app.js
const math = require('./math.js');
math.add(2, 3);
```

Теперь вникни, что здесь на самом деле происходит, потому что это корень всего
остального. `require('./math.js')` — это **буквально вызов функции прямо в этой
строке**. Когда движок до неё доходит, он останавливается, идёт на диск, читает
`math.js`, выполняет его целиком сверху донизу, забирает то, что осталось в
`module.exports`, и возвращает тебе. И только потом выполнение идёт дальше.

То есть Node узнаёт про твою зависимость **в тот момент, когда добежал до
`require`** — ни секундой раньше. Это и называется «динамическая загрузка»:
связи выясняются на ходу, в процессе выполнения.

И отсюда практическое следствие. Раз `require` — это просто код, который
выполняется, когда до него дошли, — его можно ставить **где угодно**:

```js
if (process.env.DEBUG) {
  const logger = require('./logger');   // подключим, только если нужно
}
```

Совершенно легально. Это же обычный вызов функции — какая разница, где он стоит.

Держи в голове картинку: **идёшь по коду, натыкаешься на `require` — «а, надо
подгрузить», подгрузил, пошёл дальше.** Про зависимости узнаёшь *по дороге*.

## ES Modules — «сначала разберись, потом выполняй»

Когда модули добавляли в сам язык, сделали иначе — с новыми ключевыми словами
`import` / `export`:

```js
// math.js
export function add(a, b) { return a + b; }

// app.js
import { add } from './math.js';
```

Выглядит почти так же, но механика **противоположная**, и это самое важное во
всей теме.

`import` — это **не вызов функции**. Это объявление, которое движок читает
**ещё до того, как выполнить хоть одну строку кода**. Сначала он проходит по
файлу глазами, находит все `import` и `export`, идёт по ним в другие файлы, там
снова находит их импорты — и так строит **полную карту зависимостей всего
приложения, ещё не запустив его**. И только когда карта готова — начинает
выполнять.

Формально это три фазы, но суть в первой:
1. **construct / parse** — прочитать файлы, найти все import/export, обойти весь
   граф зависимостей;
2. **instantiate / link** — завести в памяти ячейки под экспорты и связать с
   ними импорты (по ссылке — запомни, пригодится ниже);
3. **evaluate** — выполнить код модулей.

Вот почему `import` нельзя засунуть в `if`:

```js
if (x) {
  import foo from './foo.js';   // ← синтаксическая ошибка
}
```

Движку нужно построить карту зависимостей **до запуска**, то есть до того, как
он вообще узнает, чему равен `x`. Он физически не может решить, есть эта
зависимость или нет. Поэтому `import` обязан стоять статично, на верхнем уровне
файла.

Картинка: **сначала полностью составил карту («кто от кого зависит»), и только
потом поехал выполнять.** Про зависимости узнаёшь *заранее*.

> Если нужна именно условная загрузка — для этого есть отдельный **динамический
> `import()`**: он выглядит как функция, работает асинхронно и возвращает промис.
> Его как раз можно писать внутри `if`. Но это осознанное исключение, а не
> обычный `import`.

Эта разница — **«по дороге» (CJS) против «заранее» (ESM)** — и есть то, из чего
дальше растёт вообще всё: и почему `import` только наверху, и почему ESM умеет
tree-shaking (сборщик заранее видит всю карту и выкидывает то, что никто не
импортирует), и почему загрузка асинхронная, и всё, что ниже.

## Снимок против живого провода

Тонкость, которую любят на собесе, и она прямо следует из «по дороге vs
заранее».

В CJS `require` возвращает объект `module.exports`. Когда ты пишешь
`const { count } = require('./counter.js')`, ты забираешь **то, что лежит в
коробке прямо сейчас**. Это как сфотографировать полку в магазине: у тебя снимок
на момент съёмки. Продавец потом переставит товар — на твоей фотографии
по-прежнему старое.

```js
// counter.js (CJS)
let count = 0;
setInterval(() => count++, 1000);   // модуль сам меняет count у себя
module.exports = { count };

// app.js
const { count } = require('./counter.js');
// сколько ни жди — здесь всегда 0.
// ты забрал снимок значения 0, а не связь с переменной.
```

В ESM — наоборот. Импорт это **не снимок значения, а живой провод** к той самой
переменной в другом файле:

```js
// counter.mjs
export let count = 0;
setInterval(() => count++, 1000);

// app.mjs
import { count } from './counter.mjs';
// подожди пару секунд, прочитай count — увидишь 3, 4, 5...
```

Почему так? Снова из того же корня. CJS выполняет модуль как обычную функцию и
отдаёт тебе объект-результат — обычное копирование значения. А ESM ещё на этапе
построения карты (фаза link) **связал твой `import` напрямую с ячейкой памяти
чужого `export`**. Не скопировал значение — протянул ссылку. Отсюда и «вживую».

Одна оговорка: провод **односторонний, только на чтение**. Ты видишь чужие
изменения, но сам присвоить импортированной переменной (`count = 100`) не
можешь — ошибка. Меняет только тот файл, который её экспортировал.

## Кто кого может импортировать

Раз форматов два, возникает вопрос: могут ли они звать друг друга. Ответ
несимметричный — и, если понял предыдущее, теперь очевиден сам.

**ESM может тянуть CJS** — спокойно:

```js
import fs from 'fs';   // fs — старый CJS-модуль, и всё работает
```

Почему можно? ESM грузится асинхронно, у него полно времени; подождать, пока
синхронный CJS-модуль выполнится, для него не проблема. Он берёт то, что
оказалось в `module.exports`, и подставляет как `default`.

**CJS не может синхронно затянуть ESM** — вот это исторически нельзя:

```js
const stuff = require('./modern.mjs');   // ← облом
```

Почему? `require` по своей природе **синхронный** — «встань, дождись, верни
прямо сейчас». А ESM грузится **асинхронно** — ему нужно время построить карту,
что-то подгрузить. Синхронный `require` не умеет ждать асинхронное. Конфликт
характеров.

Обход — тот самый динамический `import()`, он асинхронный и возвращает промис:

```js
// внутри async-функции в CJS-файле:
const stuff = await import('./modern.mjs');   // так можно
```

Правило в голове: **вверх — можно, вниз синхронно — нет.** Новое (ESM) спокойно
тянет старое (CJS). Старое (CJS) дотянуться до нового синхронно не может —
только через асинхронный `import()`.

## Как Node понимает, какой это формат

Node решает по сигналам, по приоритету:
1. Расширение: `.mjs` — всегда ESM, `.cjs` — всегда CJS.
2. Для обычного `.js` — поле `"type"` в ближайшем `package.json`:
   - `"type": "module"` → `.js` это ESM;
   - `"type": "commonjs"` или поля нет → `.js` это CJS.

```json
// package.json
{ "type": "module" }   // теперь все .js в проекте — ESM
```

## Мелочи, которые различаются

В CJS есть «магические» переменные, которых в ESM нет, и наоборот:

- `__dirname` и `__filename` (путь к файлу и папке) — **только в CJS**. В ESM их
  собирают руками из `import.meta.url`:

```js
import { fileURLToPath } from 'node:url';
import { dirname } from 'node:path';
const __dirname = dirname(fileURLToPath(import.meta.url));
```

- **top-level await** — возможность писать `await` прямо на верхнем уровне
  модуля, без обёртки в `async function`, — есть **только в ESM**. В CJS так
  нельзя. Это не только удобство: именно из-за него сдвигается тайминг таймеров
  (следующий раздел).

## И теперь — связь с event loop (ради чего это в фидбэке)

Вспомни главную гонку из темы event loop: на верхнем уровне `setTimeout(fn, 0)`
против `setImmediate` — кто первый, непредсказуемо, потому что `setTimeout(0)`
тайно превращается в `setTimeout(1мс)`, и всё решает, успела ли пройти эта
миллисекунда.

Так вот. **Сам event loop у CJS и ESM абсолютно одинаковый** — те же фазы, те
же микротаски, тот же кламп до 1мс. Меняется только **момент, когда таймеры
вообще успевают зарегистрироваться**.

- В **CJS** модуль — это один сплошной синхронный забег сверху вниз. Прочитали
  весь файл как единый кусок, по дороге зарегистрировали `setTimeout` и
  `setImmediate`, и только потом закрутился цикл. Быстро, одним махом.
- В **ESM** старт растянутый: асинхронная загрузка, построение карты, а если
  есть `top-level await` — выполнение вообще рвётся на кусочки (код после
  `await` уезжает в микротаску).

Итог: раз в ESM старт медленнее и рваный, к моменту, когда цикл добирается до
фазы timers, та самая 1мс чаще **успевает** пройти → таймер уже «созрел» →
`setTimeout` чаще выигрывает. В CJS старт мгновенный, миллисекунда чаще **не**
успевает → чаще выигрывает `setImmediate`.

Но это по-прежнему **не гарантия, а сдвиг вероятности.** Гонка остаётся гонкой.
Единственное место, где порядок железно детерминирован, — внутри I/O-колбэка
(там `setImmediate` всегда первый, потому что фаза `check` идёт сразу за `poll`),
и это правило от формата модуля не зависит.

## Формулировка для собеса

> «CommonJS — старый Node-формат: `require`/`module.exports`. Загрузка
> синхронная и динамическая — `require` это обычный вызов функции, выполняется
> там, где стоит, поэтому его можно писать хоть в `if`; наружу отдаётся снимок
> значения. ES Modules — стандарт языка: `import`/`export`. Загрузка асинхронная
> и статическая — движок строит карту зависимостей до выполнения, поэтому
> `import` только на верхнем уровне, зато возможен tree-shaking; импорт — живая
> read-only-ссылка на чужой экспорт. ESM может тянуть CJS, обратно синхронно
> нельзя — только через динамический `import()`. Event loop у них общий, но
> top-level await и асинхронный старт ESM сдвигают момент регистрации таймеров,
> поэтому гонка `setTimeout(0)` vs `setImmediate` в ESM чаще падает в сторону
> таймера — хотя гарантий по-прежнему нет.»
