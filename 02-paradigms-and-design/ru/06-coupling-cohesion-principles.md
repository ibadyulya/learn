# Связанность, связность и базовые принципы

> 🌐 English version: [06-coupling-cohesion-principles.md](../en/06-coupling-cohesion-principles.md)

Две главные метрики качества структуры кода — плюс набор практических правил
(DRY/KISS/YAGNI, закон Деметры), которые служат тем же двум метрикам. Читается как
рассказ.

Сквозная идея темы:

> **Хорошая структура сводится к двум величинам: связность (cohesion) — насколько
> элементы внутри модуля относятся к одной задаче — её максимизируем; связанность
> (coupling) — насколько модули зависят друг от друга — её минимизируем. Цель всего
> дизайна: high cohesion + low coupling. Остальные принципы (SOLID, GRASP, DRY,
> закон Деметры) — способы её достичь.**

---

## Связность (cohesion) — «всё в модуле про одно»

Насколько элементы одного модуля/класса **относятся к одной задаче**. Высокая
связность — класс сфокусирован на одной роли; низкая — «швейцарский нож» / свалка
`utils`, где перемешаны БД, форматирование и валидация.

```ts
// Низкая связность: класс делает всё подряд
class Helper { formatDate() {} sendEmail() {} parseCsv() {} hashPassword() {} }
// Высокая: каждый про одно
class DateFormatter {} class Mailer {} class CsvParser {} class PasswordHasher {}
```
Зачем: сфокусированный модуль легче понять, менять и переиспользовать. Это прямая
родня [SRP](./03-solid.md) и High Cohesion из [GRASP](./04-grasp.md).

---

## Связанность (coupling) — «насколько модуль знает о других»

Насколько один модуль **зависит** от внутренностей другого. Сильная связанность
(tight) — модуль знает детали чужой реализации, лезет в его поля, ломается при его
изменении. Слабая (loose) — общаются через узкий стабильный интерфейс.

```ts
// Сильная: OrderService знает про конкретный Postgres и его API
class OrderService { private db = new PostgresClient(); save(o) { this.db.rawInsert(o) } }
// Слабая: зависит от абстракции, конкретику внедряют
class OrderService { constructor(private repo: OrderRepository) {} save(o) { this.repo.save(o) } }
```
Зачем: чем меньше модуль знает о других, тем безопаснее его менять, тестировать
(подставить мок) и переиспользовать. Слабая связанность — цель, ради которой
существуют DIP, интерфейсы, Pure Fabrication.

Признаки сильной связанности: цепочки `a.b.c.d`, зависимость от глобального
состояния/синглтонов, «поменял тут — сломалось там», модуль импортирует десяток
других.

---

## Почему их всегда называют парой

Они **тянут в одну сторону**: если каждый модуль сфокусирован на своей роли
(высокая связность), ему нужно меньше знать о других (низкая связанность). И
наоборот: God-класс, который делает всё, неизбежно цепляется за всё. Поэтому цель
формулируют парой — **high cohesion + low coupling**. Это, по сути, критерий «хорошо
ли разбита система на модули».

---

## Закон Деметры — «не разговаривай с незнакомцами»

Практическое правило низкой связанности: метод должен обращаться только к
**ближайшим соседям** — своим полям, аргументам, тому, что сам создал, — а не
лазить вглубь чужих объектов.

```ts
// Плохо: цепочка знает всю структуру насквозь
order.getCustomer().getAddress().getCity().toUpperCase();
// Лучше: спроси у ближайшего объекта
order.getCustomerCity();
```
Зачем: длинная цепочка `a.b.c.d` жёстко привязывает код к внутреннему устройству
всех звеньев — поменяется любое, сломается вызов. Спрашивай у того, с кем работаешь
напрямую.

---

## DRY / KISS / YAGNI — практичные напоминалки

- **DRY (Don't Repeat Yourself)** — не дублируй **знание**: одно правило живёт в
  одном месте. Осторожно: DRY про дублирование *смысла*, а не похоже выглядящего
  кода. Насильно объединить два случайно похожих куска = **связать несвязанное**
  («wrong abstraction» хуже дублирования). Дублирование дешевле неправильной
  абстракции.
- **KISS (Keep It Simple)** — простое решение предпочтительнее умного. Умный код
  дороже в поддержке.
- **YAGNI (You Aren't Gonna Need It)** — не строй впрок «на будущее». Абстракция
  под несуществующее требование = мёртвый вес и лишняя связанность. Вводи её, когда
  потребность **реально появилась** (правило трёх).

Все три — про **управление сложностью**: не добавляй её без нужды, но и не дублируй
знание.

---

## Формулировка для собеса

> «Качество структуры меряю двумя величинами: связность — насколько модуль про одну
> задачу (максимизирую, это про SRP), и связанность — насколько модули зависят друг
> от друга (минимизирую, ради этого DIP, интерфейсы, инъекция). Они парны: focused
> модуль знает о других меньше. Слабую связанность на практике держат закон Деметры
> (не лезь через `a.b.c.d`), зависимость от абстракций и узкие интерфейсы. DRY —
> одно знание в одном месте, но не путать с похожим кодом (неправильная абстракция
> хуже дублирования); KISS — проще лучше; YAGNI — не абстрагируй впрок. Всё это —
> про high cohesion + low coupling.»
