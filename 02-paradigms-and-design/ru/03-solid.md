# Принципы SOLID

> 🌐 English version: [03-solid.md](../en/03-solid.md)

Пять принципов объектно-ориентированного дизайна (Роберт Мартин). Цель — не
«красиво ради красоты», а чтобы код можно было **менять, не ломая остальное**.
Читается как рассказ: каждый принцип вводится через конкретную боль, которую он
лечит.

Сквозная идея всей темы:

> **SOLID — это пять способов сказать одно и то же: код должен быть устроен так,
> чтобы изменение требования затрагивало мало мест и не «текло» по всей системе.
> Каждая буква борется со своим видом хрупкости, но все пять — про локализацию
> изменений и управление зависимостями.**

Держи в голове главный враг: **изменение неизбежно.** Требования меняются всегда.
Плохой дизайн — это когда одно изменение расходится волной по десяткам файлов и
что-нибудь ломает по дороге. Хороший — когда изменение остаётся **локальным**.
Все пять принципов — про это.

---

## S — Single Responsibility Principle (принцип единственной ответственности)

**У класса (модуля, функции) должна быть одна причина для изменения.**

Главная путаница: «одна ответственность» ≠ «делает одну вещь». Точная
формулировка — **одна причина меняться**, то есть один «заказчик», одна ось
изменения. Класс, который считает зарплату, верстает отчёт и сохраняет в БД,
имеет **три** причины меняться (правила бухгалтерии, формат отчёта, схема БД) и
трёх разных заказчиков.

```ts
// Плохо: три причины меняться в одном классе
class Employee {
  calculatePay() { /* правила бухгалтерии */ }
  renderReport() { /* формат для HR */ }
  save()         { /* схема БД */ }
}
```
```ts
// Хорошо: каждая ось изменения — свой класс
class PayCalculator      { calculate(e: Employee): Money { /* ... */ } }
class EmployeeReport     { render(e: Employee): string   { /* ... */ } }
class EmployeeRepository { save(e: Employee): void       { /* ... */ } }
```

Зачем: когда бухгалтер меняет правила расчёта, ты трогаешь только
`PayCalculator` — отчёт и БД ни при чём, риск сломать их нулевой. **Изменение
локально.** Обратная сторона — не дроби до абсурда: класс на один метод на каждый
чих порождает россыпь мелочи. Ориентир — не «одно действие», а «один источник
требований».

## O — Open/Closed Principle (принцип открытости/закрытости)

**Сущности открыты для расширения, но закрыты для модификации** — новое
поведение добавляется, а существующий код не переписывается.

Боль, которую лечит: каждый новый случай — правка одного и того же разрастающегося
`switch`/`if-else`, который страшно трогать, потому что там же живёт проверенная
логика.

```ts
// Плохо: новый тип фигуры = правка этой функции
function area(shape: any): number {
  if (shape.kind === 'circle') return Math.PI * shape.r ** 2;
  if (shape.kind === 'square') return shape.s ** 2;
  // добавили треугольник → снова лезем СЮДА, рискуя сломать круг и квадрат
}
```
```ts
// Хорошо: расширяем добавлением класса, area() не трогаем
interface Shape { area(): number }
class Circle implements Shape { constructor(private r: number) {} area() { return Math.PI * this.r ** 2 } }
class Square implements Shape { constructor(private s: number) {} area() { return this.s ** 2 } }
// новый треугольник = новый класс Triangle implements Shape; старый код не меняется
```

Механизм — **полиморфизм**: общий интерфейс + новые реализации. Зачем: новый
функционал физически не может сломать проверенный старый, потому что старый код не
трогается.

Честная оговорка: OCP — не абсолют. Заранее все оси расширения не угадать, а
абстракция «на всякий случай» — оверинжиниринг. Закрывать стоит там, где изменения
уже **повторяются** (второй, третий такой же `if` — сигнал вынести в полиморфизм).

## L — Liskov Substitution Principle (принцип подстановки Барбары Лисков)

**Объект подтипа должен подставляться вместо базового типа без нарушения
корректности программы.** Наследник не имеет права «врать» о контракте предка.

Боль: наследование по внешней форме, а не по поведению. Классика — `Square extends
Rectangle`. У прямоугольника ширина и высота независимы; у квадрата — нет. Код,
корректный для `Rectangle`, ломается, когда ему подсунули `Square`:

```ts
class Rectangle {
  constructor(protected w: number, protected h: number) {}
  setW(w: number) { this.w = w }
  setH(h: number) { this.h = h }
  area() { return this.w * this.h }
}
class Square extends Rectangle {
  setW(w: number) { this.w = w; this.h = w }   // ломает независимость сторон
  setH(h: number) { this.w = h; this.h = h }
}

function stretch(r: Rectangle) {
  r.setW(5); r.setH(4);
  console.assert(r.area() === 20);   // Rectangle → 20; Square → 16, падает
}
```

Признаки нарушения LSP: наследник **бросает исключение** там, где базовый работает;
**усиливает предусловия** (требует больше, чем предок); **ослабляет постусловия**
(гарантирует меньше); методы-заглушки `NotImplemented`.

Зачем это критично: полиморфизм — и, значит, OCP — **держится на LSP**. Если
подтип нельзя честно подставить, весь полиморфный код превращается в минное поле
из `if (x instanceof ...)`. Лечение — **композиция вместо наследования** и
моделирование по поведению, а не по «звучит похоже» (квадрат — это не
разновидность изменяемого прямоугольника).

## I — Interface Segregation Principle (принцип разделения интерфейсов)

**Клиента нельзя заставлять зависеть от методов, которые он не использует.** Лучше
несколько узких интерфейсов, чем один «толстый».

Боль: жирный интерфейс заставляет реализующие классы тащить ненужное — обычно
через заглушки `throw`, — и любое изменение интерфейса задевает даже тех, кому эти
методы не сдались.

```ts
// Плохо: один толстый интерфейс
interface Worker { work(): void; eat(): void }
class Robot implements Worker {
  work() { /* ... */ }
  eat()  { throw new Error('робот не ест') }   // запах: реализуем ненужное
}
```
```ts
// Хорошо: разбить по ролям
interface Workable { work(): void }
interface Eatable  { eat(): void }
class Robot implements Workable          { work() {} }
class Human implements Workable, Eatable { work() {} eat() {} }
```

Зачем: узкие интерфейсы = меньше ложных зависимостей, меньше вынужденных заглушек,
изменения не расходятся. По сути **ISP — это SRP на уровне интерфейсов**: у
интерфейса тоже должна быть одна роль.

## D — Dependency Inversion Principle (принцип инверсии зависимостей)

**Модули высокого уровня не должны зависеть от модулей низкого уровня — оба
зависят от абстракций.** И абстракции не зависят от деталей; детали зависят от
абстракций.

Боль: бизнес-логика напрямую создаёт и зовёт конкретную БД/сервис — её нельзя ни
переиспользовать, ни протестировать, ни заменить хранилище, всё прибито гвоздями.

```ts
// Плохо: высокий уровень прибит к конкретике
class OrderService {
  private db = new PostgresClient();     // жёсткая связь
  place(o: Order) { this.db.insert(o) }
}
```
```ts
// Хорошо: зависим от абстракции, конкретику внедряем снаружи
interface OrderRepository { save(o: Order): void }

class OrderService {
  constructor(private repo: OrderRepository) {}   // внедрение зависимости
  place(o: Order) { this.repo.save(o) }
}
class PostgresOrderRepo implements OrderRepository { save(o: Order) { /* ... */ } }
class InMemoryOrderRepo implements OrderRepository { save(o: Order) { /* для тестов */ } }
```

Что «инвертируется»: раньше `OrderService` (высокий уровень) зависел от
`PostgresClient` (низкий). Теперь **оба зависят от интерфейса** `OrderRepository`.
Стрелка зависимости от деталей развернулась к абстракции. Отсюда — подмена на
`InMemoryOrderRepo` в тестах, смена БД в проде без правки логики.

Не путать три вещи:
- **DIP** — *принцип*: зависеть от абстракций.
- **DI (dependency injection)** — *приём*: передавать зависимости снаружи
  (через конструктор), а не создавать внутри. Способ достичь DIP.
- **IoC (inversion of control)** — общий зонтик про «управление отдаёт наружу»;
  DI-контейнеры (в том числе в NestJS) — его реализация.

## Как пять принципов держатся вместе

Они не независимы — это одна идея под пятью углами:
- **SRP** и **ISP** — про то, чтобы у класса/интерфейса была одна роль (ISP = SRP
  для интерфейсов).
- **OCP** — цель (расширять, не трогая старое) — **достижима только через
  полиморфизм**, а полиморфизм корректен **только при LSP**. Значит OCP стоит на
  LSP.
- **DIP** делает OCP возможным на уровне модулей: подменять реализацию за
  интерфейсом = расширять систему, не меняя её ядро.

Общий знаменатель — **управляй зависимостями и локализуй изменения.**

---

## Формулировка для собеса

> «SOLID — пять принципов, служащих одной цели: чтобы изменение требования было
> локальным. SRP — один класс, одна причина меняться (не путать с «делает одно»).
> OCP — новое поведение добавляем через полиморфизм, не переписывая проверенный
> код. LSP — подтип обязан честно подставляться вместо базового, иначе полиморфизм
> (и OCP) ломается; классический контрпример — Square/Rectangle. ISP — узкие
> интерфейсы вместо толстых, чтобы клиент не зависел от лишнего; это SRP для
> интерфейсов. DIP — высокий и низкий уровни зависят от абстракции, а не друг от
> друга; на практике достигается через dependency injection и лежит в основе
> DI-контейнеров вроде Nest.»
