# Паттерны проектирования (Gang of Four)

> 🌐 English version: [05-design-patterns-gof.md](../en/05-design-patterns-gof.md)

23 классических паттерна из книги «банды четырёх». Читается как рассказ: паттерн —
это **не код для копирования, а именованное решение повторяющейся проблемы
проектирования**. Ценность на собесе — не вызубрить 23 штуки, а узнавать проблему
и называть решение (и не тащить паттерн туда, где он не нужен).

Сквозная идея всей темы:

> **GoF делит паттерны на три семьи по типу проблемы: как *создавать* объекты
> (порождающие), как из объектов *собирать структуры* (структурные), как объекты
> *взаимодействуют и распределяют обязанности* (поведенческие). Зная семью, ты уже
> наполовину назвал паттерн.**

Ниже — не все 23, а те ~10, что реально спрашивают и что ты каждый день видишь в
JS/Node/React/Nest.

---

## Порождающие — как создавать объекты

Проблема семьи: прямой `new ConcreteThing()` намертво привязывает код к
конкретному классу. Порождающие прячут создание за абстракцией.

**Factory Method (фабричный метод).** Вместо `new` — метод, который решает, какой
объект создать. Клиент просит «дай подходящий объект», не зная конкретного класса.
```ts
interface Button { render(): string }
class HtmlButton implements Button { render() { return '<button>' } }
class IosButton  implements Button { render() { return 'UIButton' } }

function createButton(os: 'web' | 'ios'): Button {
  return os === 'ios' ? new IosButton() : new HtmlButton();
}
```
Зачем: добавить новую платформу = новый класс + ветка в фабрике, а весь клиентский
код (`btn.render()`) не трогается — прямое OCP.

**Abstract Factory** — фабрика семейств связанных объектов (кнопка + чекбокс + окно
одного стиля). Тот же принцип, но создаёт согласованный *набор*.

**Singleton (одиночка).** Гарантирует **один** экземпляр на всё приложение и
глобальную точку доступа (конфиг, пул соединений, логгер).
```ts
class Config {
  private static instance: Config;
  private constructor() {}
  static get(): Config { return this.instance ??= new Config(); }
}
```
Осторожно: часто **антипаттерн** — это глобальное состояние, прячет зависимости,
мешает тестам. В JS модуль сам по себе синглтон (кэшируется), а в Nest синглтон
даёт DI-контейнер (scope по умолчанию) — руками почти не нужен.

**Builder (строитель).** Пошаговая сборка сложного объекта, когда конструктор с
десятью аргументами превращается в кашу.
```ts
new QueryBuilder().select('id').from('users').where('age > 18').build();
```
Зачем: читаемо, части опциональны, порядок гибкий. Видел в query-билдерах,
`supertest`, конфигурировании.

## Структурные — как собирать объекты в структуры

Проблема семьи: как соединить объекты/классы в большие структуры, не превращая всё
в жёсткий монолит.

**Adapter (адаптер).** Оборачивает несовместимый интерфейс в тот, что ждёт клиент.
«Переходник».
```ts
// клиент ждёт Logger.log(); сторонняя либа даёт winston.info()
class WinstonAdapter implements Logger {
  constructor(private w: Winston) {}
  log(msg: string) { this.w.info(msg); }
}
```
Зачем: подружить чужой код с твоим контрактом, не переписывая ни того, ни другого.

**Decorator (декоратор).** Добавляет поведение объекту, **оборачивая** его,
сохраняя тот же интерфейс. Альтернатива взрыву подклассов.
```ts
interface Coffee { cost(): number }
class Espresso implements Coffee { cost() { return 2 } }
class WithMilk implements Coffee {
  constructor(private c: Coffee) {}
  cost() { return this.c.cost() + 0.5 }   // оборачивает и дополняет
}
new WithMilk(new Espresso()).cost(); // 2.5
```
Зачем: комбинировать поведения динамически (`WithMilk(WithSugar(Espresso))`) без
класса на каждую комбинацию. Видел в middleware Express, интерцепторах Nest,
декораторах TS.

**Facade (фасад).** Один простой интерфейс поверх сложной подсистемы. Прячет
кучу деталей за одним методом.
```ts
class OrderFacade {
  place(cart: Cart) { this.stock.reserve(cart); this.pay.charge(cart); this.ship.schedule(cart); }
}
```
Зачем: клиент зовёт `facade.place()`, не зная про склад/оплату/доставку. Снижает
связанность.

**Proxy (заместитель).** Объект-подставка с тем же интерфейсом, контролирующий
доступ к настоящему: ленивая инициализация, кэш, права, логирование.
```ts
class CachingApiProxy implements Api {
  private cache = new Map();
  constructor(private real: Api) {}
  get(id: string) { return this.cache.get(id) ?? this.cache.set(id, this.real.get(id)).get(id); }
}
```
Зачем: добавить контроль доступа/кэш, не меняя клиента и реальный объект. `Proxy`
даже встроен в язык JS.

> Adapter vs Facade vs Decorator (частый вопрос): **Adapter меняет интерфейс**
> (несовместимый → нужный), **Facade упрощает** (много → один), **Decorator
> сохраняет интерфейс и добавляет поведение** (тот же → тот же + фича).

## Поведенческие — как объекты взаимодействуют

Проблема семьи: как распределить обязанности и организовать общение между
объектами.

**Strategy (стратегия).** Семейство взаимозаменяемых алгоритмов за общим
интерфейсом; клиент выбирает нужный в рантайме. (Уже всплывало в [SOLID](./03-solid.md)
как способ выполнить OCP.)
```ts
interface SortStrategy { sort(a: number[]): number[] }
class QuickSort implements SortStrategy { sort(a) { /* ... */ return a } }
class Sorter { constructor(private s: SortStrategy) {} run(a: number[]) { return this.s.sort(a) } }
```
Зачем: вместо `if (type===...)` — подставляемый объект-алгоритм. Новый алгоритм =
новый класс.

**Observer (наблюдатель).** Объект («субъект») уведомляет подписчиков об
изменениях, не зная, кто они. Основа реактивности и событий.
```ts
class Subject {
  private subs: ((v: number) => void)[] = [];
  subscribe(fn: (v: number) => void) { this.subs.push(fn) }
  emit(v: number) { this.subs.forEach(fn => fn(v)) }
}
```
Зачем: расцепить источник события и реакции. Видел везде: `EventEmitter` в Node,
RxJS, реактивность Vue, `addEventListener`, стор-подписки.

**Command (команда).** Упаковывает действие в объект: его можно передать,
поставить в очередь, залогировать, отменить (undo).
```ts
interface Command { execute(): void; undo(): void }
class AddText implements Command {
  constructor(private doc: Doc, private text: string) {}
  execute() { this.doc.append(this.text) }
  undo()    { this.doc.removeLast(this.text.length) }
}
```
Зачем: undo/redo, очереди задач, транзакционность. Действие становится данными.

Ещё из поведенческих (назвать, если спросят): **State** (объект меняет поведение
со сменой внутреннего состояния — похож на Strategy, но переключается сам),
**Iterator** (обход коллекции без раскрытия устройства — в JS это `Symbol.iterator`),
**Template Method** (скелет алгоритма в базовом классе, шаги — в наследниках),
**Chain of Responsibility** (запрос идёт по цепочке обработчиков — как middleware).

## Главное предостережение

Паттерны — **словарь**, а не цель. Насильно впихнутый паттерн (AbstractFactory там,
где хватило бы функции) — это оверинжиниринг. Правильный ход: **сначала проблема,
потом — а нет ли для неё именованного решения**. И половина «паттернов» в JS
выражается проще: стратегия — это просто функция-параметр, синглтон — модуль,
команда — замыкание.

## Формулировка для собеса

> «Паттерны GoF — именованные решения типовых проблем проектирования, разбитые на
> три семьи. Порождающие (Factory Method, Singleton, Builder) прячут создание
> объектов за абстракцией. Структурные (Adapter, Decorator, Facade, Proxy) собирают
> объекты в структуры: адаптер меняет интерфейс, фасад упрощает, декоратор
> оборачивает и добавляет поведение, прокси контролирует доступ. Поведенческие
> (Strategy, Observer, Command) организуют взаимодействие: стратегия — сменные
> алгоритмы, наблюдатель — подписки/события (EventEmitter, RxJS), команда —
> действие как объект с undo. В JS многие выражаются проще — функцией, модулем,
> замыканием, — и паттерн нужен только когда проблема реально повторяется.»
