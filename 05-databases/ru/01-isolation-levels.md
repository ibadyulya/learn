# Уровни изоляции транзакций

> 🌐 English version: [01-isolation-levels.md](../en/01-isolation-levels.md)

Сквозная идея темы:

> **Транзакция хочет притвориться, будто она в базе одна. Но параллельно бегут
> другие транзакции и «протекают» в неё. Уровень изоляции — это ручка «насколько
> сильно я готов терпеть чужие протечки в обмен на скорость». Выше изоляция →
> меньше протечек, но меньше параллелизма.**

Задачи для самопроверки — [01-isolation-levels.tasks.md](./01-isolation-levels.tasks.md),
разборы — [01-isolation-levels.answers.md](./01-isolation-levels.answers.md).

---

## Изоляция — это «I» в ACID

ACID — гарантии транзакции:
- **A — Atomicity:** всё или ничего; упало на полпути — откат целиком.
- **C — Consistency:** транзакция переводит БД из одного корректного состояния в
  другое, не нарушая constraints/внешних ключей.
- **I — Isolation:** ← **наша тема.** Параллельные транзакции не мешают друг
  другу; в идеале каждая выполняется, будто она одна.
- **D — Durability:** закоммитил — переживёт падение (записано на диск).

Изоляция — единственная буква про то, **что происходит, когда транзакций много
одновременно.** Остальные — про одну.

## Идеал — «как будто по очереди»

Золотой стандарт корректности — **serializability (сериализуемость)**: результат
параллельного выполнения = как если бы транзакции шли **строго по очереди**, одна
за другой. Тогда параллелизма «не видно», каждая живёт в иллюзии одиночества.

Проблема: **это дорого** — много блокировок или откатов, параллелизм падает.
Отсюда компромисс: разрешить немного протечек ради скорости → градация уровней.
Но чтобы понимать, что именно ты разрешаешь, надо знать сами протечки —
**аномалии**.

---

## Три аномалии — способы «протечь»

Ядро темы: уровни определяются тем, **какие аномалии они запрещают.** Три штуки
по классическому SQL-стандарту, по нарастанию «масштаба протечки».

### 1. Dirty read — прочитал чужое НЕзакоммиченное
Читаешь данные, которые другая транзакция изменила, но **ещё не закоммитила**; а
она **откатывается** — и ты работал с тем, чего **никогда не было**.
```
T1: UPDATE balance SET amount=500 WHERE id=1;   -- ещё НЕ commit
T2:   SELECT amount FROM balance WHERE id=1;      -- читает 500 (грязное!)
T1: ROLLBACK;                                      -- вернулось 100
-- T2 решила на основе 500, которых не существовало
```

### 2. Non-repeatable read — прочитал строку дважды, значения разные
Читаешь одну **строку** дважды, получаешь **разное**, потому что другая транзакция
между чтениями изменила её и **закоммитила**.
```
T1: SELECT amount FROM balance WHERE id=1;        -- 100
T2:   UPDATE balance SET amount=500 WHERE id=1; COMMIT;
T1: SELECT amount FROM balance WHERE id=1;        -- 500 (та же строка!)
```
Отличие от dirty: тут T2 **закоммитила** (данные настоящие). Проблема — одна
транзакция видит **несогласованную картину**: почва уплыла под ногами.

### 3. Phantom read — тот же запрос вернул РАЗНЫЙ НАБОР строк
Дважды делаешь запрос **с условием**, во второй раз строк больше/меньше, потому
что другая транзакция **вставила/удалила** подходящие и закоммитила.
```
T1: SELECT * FROM orders WHERE amount > 100;      -- 3 строки
T2:   INSERT INTO orders (amount) VALUES (200); COMMIT;
T1: SELECT * FROM orders WHERE amount > 100;      -- 4 строки (фантом)
```
Отличие от non-repeatable: там менялось **значение строки** (`UPDATE`), тут —
**набор строк** (`INSERT`/`DELETE`).

| Аномалия | Что протекло | Чужая операция |
|---|---|---|
| **Dirty read** | незакоммиченное значение | незавершённый `UPDATE` |
| **Non-repeatable read** | закоммиченное изменение **строки** | закоммиченный `UPDATE` |
| **Phantom read** | закоммиченное изменение **набора строк** | закоммиченный `INSERT`/`DELETE` |

Порядок «от самой грязной к самой тонкой» — уровни отсекают их **ровно в этом
порядке, снизу вверх.**

## Четыре уровня — каждый отрезает ещё одну аномалию

### 1. Read Uncommitted — «читаю всё, даже черновики»
Видишь даже незакоммиченные чужие изменения. Не защищает **ни от чего**.
Практически не используют. (В Postgres его нет — даёт Read Committed.)

### 2. Read Committed — «читаю только закоммиченное»
Видишь только закоммиченные данные. ✅ убирает **dirty read**; ❌ non-repeatable
и phantom остаются. Причина: гарантия на уровне **отдельного запроса** — каждый
`SELECT` видит свежий снимок на свой момент, между ними мир меняется.
> **Дефолт в PostgreSQL** (и Oracle, SQL Server).

### 3. Repeatable Read — «строки не меняются под ногами всю транзакцию»
Гарантия поднята с запроса на **всю транзакцию** — обычно через **snapshot**
(«фотография» БД в начале). ✅ убирает **dirty + non-repeatable**; ❌ по стандарту
**phantom остаётся** (заморожены прочитанные строки, а не новые).
> **Подвох для собеса.** **Дефолт в MySQL (InnoDB)**, и его реализация (MVCC +
> gap locks) фантомы **на практике не даёт** — строже стандарта. В **PostgreSQL**
> этот уровень = snapshot isolation, обычные фантомы тоже отсекает. Говорить так:
> «по SQL-стандарту RR допускает phantom, но MySQL InnoDB и Postgres на практике
> его в основном предотвращают». Различие «стандарт vs реальная БД» любят.

### 4. Serializable — «как будто по очереди»
Результат = как при строго последовательном выполнении. ✅ убирает **все три** и
любые эффекты параллелизма. Цена высшая: агрессивные блокировки либо (Postgres —
**SSI, Serializable Snapshot Isolation**) отслеживание конфликтов и **откат**
одной транзакции с ошибкой сериализации → её надо **ретраить**.

## Итоговая таблица

| Уровень | Dirty | Non-repeatable | Phantom |
|---|:---:|:---:|:---:|
| **Read Uncommitted** | ❌ | ❌ | ❌ |
| **Read Committed** | ✅ | ❌ | ❌ |
| **Repeatable Read** | ✅ | ✅ | ❌¹ |
| **Serializable** | ✅ | ✅ | ✅ |

✅ = аномалия запрещена. ¹ по стандарту возможен; в MySQL InnoDB и Postgres на
практике обычно нет. **Лесенка:** каждый уровень запрещает на одну аномалию
больше, в порядке dirty → non-repeatable → phantom.

## Трейд-офф
```
слабее (Read Uncommitted) ←—————————→ строже (Serializable)
больше параллелизма, быстрее     меньше протечек, правильнее
меньше блокировок/откатов        больше блокировок / ретраев
```
Выбор по задаче (как CAP): аналитика/дашборды → **Read Committed** хватает;
финансы/переводы → **Serializable** (готовь ретраи на serialization failure).

> Формулировка: «Уровень изоляции — компромисс между корректностью и
> параллелизмом. Три аномалии по нарастанию: dirty read (чужое незакоммиченное),
> non-repeatable (строка изменилась между чтениями), phantom (изменился набор
> строк). Read Uncommitted не защищает ни от чего, Read Committed убирает dirty
> (дефолт Postgres), Repeatable Read — ещё и non-repeatable (дефолт MySQL),
> Serializable — всё, как будто по очереди. По стандарту RR допускает phantom, но
> MySQL и Postgres на практике предотвращают. Чем строже — тем меньше параллелизм
> и больше блокировок или откатов с ретраями.»
