# Блокировки и MVCC

> 🌐 English version: [05-locking-mvcc.md](../en/05-locking-mvcc.md)

Как БД реализует изоляцию под капотом. Читается как рассказ; продолжение
[уровней изоляции](./01-isolation-levels.md).

Сквозная идея темы:

> **Чтобы параллельные транзакции не мешали друг другу, у БД два инструмента:
> блокировать доступ (locks) или давать каждому свой снимок данных (MVCC).
> Блокировки бывают пессимистичные (запрети заранее) и оптимистичные (проверь при
> коммите). MVCC — ключевая идея современных БД: читатели не блокируют писателей.**

---

## Пессимистичные блокировки — «запрети заранее»

Исходишь из того, что конфликт **вероятен**, поэтому **блокируешь** данные, пока
работаешь. Другие ждут.
```sql
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;   -- взял блокировку строки
-- пока не COMMIT/ROLLBACK, другие транзакции ждут эту строку
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;                                            -- блокировка снята
```
Виды: **shared (S, на чтение)** — несколько читателей одновременно; **exclusive
(X, на запись)** — только один. Хорошо при **высокой конкуренции** (много правок одной
строки), но снижает параллелизм — другие ждут.

## Оптимистичные блокировки — «проверь при коммите»

Исходишь из того, что конфликт **редок**: работаешь без блокировки, а при записи
**проверяешь**, не изменил ли кто-то данные тем временем. Обычно через **колонку-версию**:
```sql
UPDATE items SET price = 200, version = version + 1
WHERE id = 1 AND version = 5;    -- 0 строк обновлено → кто-то опередил → повторить
```
Если версия не совпала — конфликт, транзакцию **повторяют** (retry). Хорошо при
**низкой конкуренции**: нет накладных на блокировки, но при частых конфликтах много
ретраев.

> Правило: **много конфликтов → пессимистично; мало → оптимистично.**

---

## Дедлоки

Две транзакции ждут блокировки друг друга по кругу: T1 держит A и ждёт B, T2 держит
B и ждёт A — **никто не сдвинется**. БД **обнаруживает** цикл ожидания и **прерывает**
одну транзакцию (жертву) с ошибкой, чтобы разорвать тупик; приложение её повторяет.
Профилактика: брать блокировки **в одном порядке**, держать транзакции короткими.

---

## MVCC — многоверсионность

Ключевая идея, на которой стоят Postgres и InnoDB. Вместо того чтобы блокировать
чтения, БД хранит **несколько версий** строки. Каждая транзакция видит **снимок**
данных на свой момент.
```
Правило MVCC: читатели не блокируют писателей, писатели не блокируют читателей.
```
Как: при изменении строка не перезаписывается на месте — создаётся **новая версия**, а
старая остаётся для транзакций, которым она ещё «видна» (по времени старта/номеру
транзакции). Читающий берёт подходящую версию из цепочки, не дожидаясь пишущего.

Выгода — **высокий параллелизм**: длинный `SELECT` не тормозит `UPDATE` и наоборот. На
MVCC реализованы Read Committed и snapshot-изоляция (RR в Postgres). Плата — старые
версии надо **чистить** (в Postgres — `VACUUM`).

---

## Как это ложится на уровни изоляции

- **Read Committed / Repeatable Read** обычно на **MVCC** — снимок без блокировки
  чтений (см. [isolation-levels](./01-isolation-levels.md)).
- **Serializable** — либо агрессивные блокировки, либо (Postgres) **SSI** поверх MVCC:
  отслеживает конфликты и откатывает опасную транзакцию с ошибкой сериализации.

---

## Формулировка для собеса

> «Изоляцию БД реализует блокировками или MVCC. Пессимистичные блокировки (`SELECT ...
> FOR UPDATE`, shared/exclusive) запрещают доступ заранее — хороши при высокой
> конкуренции, но снижают параллелизм. Оптимистичные (колонка-версия, проверка при
> UPDATE) исходят из редких конфликтов — без блокировок, но с ретраями при коллизии.
> Взаимное ожидание блокировок даёт дедлок — БД детектит цикл и откатывает жертву;
> лечится единым порядком блокировок и короткими транзакциями. MVCC — многоверсионность:
> каждая транзакция видит свой снимок, читатели не блокируют писателей и наоборот; на
> нём стоят Postgres/InnoDB, плата — очистка старых версий (VACUUM).»
