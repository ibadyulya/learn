# MongoDB и Redis

> 🌐 English version: [08-mongodb-redis.md](../en/08-mongodb-redis.md)

Два самых ходовых NoSQL-хранилища и когда какое брать. Читается как рассказ;
продолжение [SQL vs NoSQL](./03-sql-vs-nosql.md).

Сквозная идея темы:

> **MongoDB — документная БД: гибкие JSON-подобные документы, богатые запросы и
> агрегация; берут, когда данные ложатся в документ и схема эволюционирует. Redis —
> in-memory key-value стор: сверхбыстрый, для кэша/сессий/счётчиков/очередей. Это
> инструменты под разные задачи, а не «замена SQL».**

---

## MongoDB — документная БД

Данные — **документы** (BSON, по сути JSON) в **коллекциях**. Схема гибкая: документы
одной коллекции могут отличаться полями.
```js
db.orders.insertOne({
  _id: 1,
  customer: { name: "Ann", email: "ann@x.com" },   // вложенный объект
  items: [{ product: "Book", qty: 2 }],            // массив
  total: 20
});
db.orders.find({ "customer.name": "Ann", total: { $gt: 10 } });
```
Есть **индексы** (в т.ч. по вложенным полям и массивам), **агрегационный конвейер**
(`$match → $group → $sort` — как SQL GROUP BY, но пошагово), с недавних версий —
**многодокументные транзакции**.

**Embedding vs referencing** — ключевое проектное решение:
- **встраивание** (вложить items прямо в order) — читается одним запросом, атомарно
  обновляется; хорошо для «читается вместе, ограничено по размеру»;
- **ссылки** (хранить `customer_id`, как в SQL) — против дублирования и для связей
  «многие-ко-многим»/больших/растущих коллекций.
Правило Mongo: моделируй **под запросы** («что читаем вместе»), а не под сущности.

Хорош для: гибкой/эволюционирующей схемы, самодостаточных документов (профиль, заказ),
горизонтального масштаба (шардинг встроен). Слаб там, где много сложных связей и JOIN —
это территория SQL.

---

## Redis — in-memory key-value стор

Данные живут **в оперативной памяти** → микросекундные задержки. Не только «строка →
строка», а богатые структуры:
- **типы:** string, hash, list, set, sorted set (zset), + TTL на ключ;
- **применение:** кэш, сессии, счётчики/rate limiting, очереди, pub/sub, лидерборды
  (zset), распределённые локи (подробно — в
  [caching-redis](../../04-backend/ru/06-caching-redis.md)).

**Персистентность** (Redis не только «кэш, что не жалко»):
- **RDB** — периодические снапшоты на диск (быстрый рестарт, но можно потерять
  последние секунды);
- **AOF** — журнал всех операций (надёжнее, медленнее/больше).
Можно комбинировать. Но всё равно рабочий набор должен **влезать в память**.

Redis **однопоточный по командам** → простые операции атомарны без блокировок, но
тяжёлую команду нельзя «размазать» по ядрам.

---

## Когда что

- **PostgreSQL/SQL** — связанные транзакционные данные, целостность, сложные запросы.
- **MongoDB** — документо-ориентированные данные, гибкая схема, самодостаточные записи,
  масштаб чтений.
- **Redis** — скорость: кэш, сессии, эфемерное состояние, счётчики, очереди.

Часто **вместе** (polyglot persistence): Postgres как источник истины + Redis как кэш +
Mongo/Elastic под свою модель.

---

## Формулировка для собеса

> «MongoDB — документная БД: гибкие JSON-документы в коллекциях, индексы по вложенным
> полям, агрегационный конвейер, есть многодокументные транзакции. Ключевое решение —
> embedding (читать одним запросом, атомарно) vs referencing (против дублирования, для
> связей); моделирую под запросы. Redis — in-memory key-value с богатыми структурами
> (hash/list/set/zset) и TTL, для кэша, сессий, rate limiting, очередей, локов;
> персистентность через RDB-снапшоты или AOF-журнал, но данные должны влезать в память,
> и он однопоточный по командам. Беру их не «вместо SQL», а под свою задачу — обычно в
> связке (polyglot persistence).»
