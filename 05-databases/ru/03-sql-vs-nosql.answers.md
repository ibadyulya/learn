# SQL против NoSQL — разборы

## Вопрос 1
**Реляционная** — данные в таблицах со строгой схемой, связаны ключами, соединяются
JOIN; **нереляционная** — документы/пары ключ-значение/колонки/графы с гибкой схемой.
Сила SQL — **целостность и транзакции** (constraints, ACID, сложные запросы); слабость
— **жёсткая схема** (миграции) и трудное горизонтальное масштабирование (шардинг).

## Вопрос 2
Нет, это семья. Семейства:
- **документные** (Mongo) — профиль/заказ как вложенный документ;
- **key-value** (Redis) — кэш, сессии;
- **колоночные** (Cassandra) — огромные объёмы, аналитика/потоковая запись;
- **графовые** (Neo4j) — соцсети, рекомендации (обход связей).

## Вопрос 3
- **Schema-on-write** (SQL): структура задана заранее, БД проверяет **при записи** →
  данные единообразны, но менять схему дорого (миграции).
- **Schema-on-read** (документные NoSQL): пишешь что угодно, форму трактует приложение
  **при чтении** → гибко, быстро эволюционирует, но нет гарантии единообразия
  (ответственность на приложении).

## Вопрос 4
- **ACID** — Atomicity, Consistency, Isolation, Durability: строгие транзакционные
  гарантии (типично для SQL).
- **BASE** — Basically Available, Soft state, Eventually consistent: доступность и
  масштаб ценой мгновенной согласованности (многие NoSQL).
Связь с **CAP**: при распределённости выбираешь между сильной согласованностью (ACID/CP)
и доступностью/масштабом (BASE/AP) — это тот же трейд-офф.

## Вопрос 5
- **SQL** — заказы/платежи: связанные данные, нужны транзакции и целостность (списать
  деньги и создать заказ атомарно), сложные отчёты с JOIN.
- **Документный NoSQL** — каталог товаров/CMS: разнородные, эволюционирующие записи,
  каждая самодостаточна как документ, нужен горизонтальный масштаб чтений.

## Вопрос 6
**Polyglot persistence** — использовать разные хранилища под разные задачи в одном
продукте, а не «одна БД на всё». Пример: **PostgreSQL** для заказов/пользователей
(транзакции) + **Redis** для кэша и сессий + **Elasticsearch** для полнотекстового
поиска. Каждое — под свою сильную сторону.

## Вопрос 7
Поверхностно, потому что: (1) SQL **масштабируется** — репликами (чтения), шардингом
(записи), просто это сложнее, чем в NoSQL; (2) Mongo не «бесплатно масштабируется» —
платишь ослабленной согласованностью и потерей JOIN/транзакций; (3) выбор — по **модели
данных и требованиям к согласованности**, а не по «масштабируется/нет». Для связанных
транзакционных данных Mongo может быть **хуже**. Правильный ответ — «зависит от задачи».
